## 1. Слабые места и риски

Критический = утечка между ресторанами или нарушение учёта; высокий = существенная потеря доверия, денег или возможность эксплуатации.

| Риск | Серьёзность и сценарий | Необходимое изменение |
|---|---|---|
| RLS обходится сервером | **Критический.** `recognize` принимает ID чужого файла; сервер с service role читает его, хотя REST закрыт RLS. Аналогично RPC, экспорт, история, фоновые задания. | Пользовательские чтения — с JWT пользователя; привилегированные операции — с повторной проверкой актуального membership и принадлежности всех ID. Запретить прямые записи REST, обходящие валидатор/подтверждение. RPC: ограниченный EXECUTE, закреплённый search_path, минимум привилегий. Составные FK `(restaurant_id, id)` для связей таблиц. Отдельные тесты RPC/Edge/Storage/list/signed URL, а не только SELECT таблиц. |
| Роли и приглашения | **Высокий.** Manager меняет membership через REST, принимает чужое приглашение или продолжает работать после отзыва прав. | Роли меняет только сервер; приглашение одноразовое, привязано к ресторану, роли и подтверждённому email. Зафиксировать передачу владения, запрет потери последнего owner, отзыв доступа. Роль проверять при commit; JWT с устаревшей ролью недостаточен. |
| Storage и локальные черновики | **Высокий.** Подмена пути, перезапись файла после проверки, ссылка остаётся доступной после исключения управляющего, черновик прошлого ресторана виден при переключении. | Приватный bucket; политики на каждую операцию и bucket/path; серверные имена, immutable-файлы с hash/version; короткие signed URL с принятой границей отзыва. Кеши и черновики разделять по user + restaurant + documentId; очищать при выходе. |
| Подтверждение накладной | **Критический.** Два подтверждения или потеря ответа дают двойной приход; обновление цен проходит, INSERT движения падает. | Одна транзакция Postgres, описанная в п. 4.3. Нужны одновременно opId и бизнес-уникальность прихода по invoice/line; один opId не спасает от повторной загрузки того же счёта с новым ID. |
| Валидация состояния вместо перехода | **Критический.** Полностью валидный JSON содержит переписанную историю цен или удалённый ингредиент с движениями. | На сервере обязательны `assertValidDocument` **и** `assertValidTransition`, плюс проверки связей с журналами. В черновике явно названа только schema.js. Общая схема сама по себе append-only не обеспечивает. |
| Import/reset/restore | **Критический.** Восстановили каталог до прихода; статус confirmed и склад остались прежними. Или импорт удалил ID с движениями. | Не переносить все операции старого StorageAdapter без изменений. При наличии журналов — запрет произвольной замены каталога; миграция/архивирование и отдельный согласованный restore. Исправления подтверждённых документов — компенсирующие записи, не удаление истории. |
| Совместная работа | **Высокий.** Управляющий подтверждает накладную, пока owner редактирует другое блюдо; весь документ конфликтует. Изменились последствия цены после предпросмотра. | CAS предотвращает потерю, но не разрешает конфликт. Сохранять черновик, перечитывать, повторно показывать изменившиеся последствия. Invoice draft имеет собственную версию. Разные рецепты/поставщики не должны постоянно мешать друг другу. Цена по документу не объединяется общим merge автоматически. |
| Рост документа | **Высокий, проверен экспериментом.** История и snapshots сценариев заполняют лимит; каждый save валидирует/передаёт большой каталог, история и WAL усиливают запись. | Не объявлять цель «много ресторанов и годы» закрытой без size/latency/conflict бюджета. Перед открытым E вынести растущие price events из постоянно перезаписываемого JSON; каталог для calc собирать адаптером. Не хранить одну и ту же историю авторитетно в двух местах. Для пилота возможен ограниченный документ с измеряемым порогом миграции. |
| Цена и дата | **Высокий.** Старую накладную загрузили сегодня — её цена стала текущей; два поставщика одного ингредиента постоянно перетирают друг друга. | Разделить invoiceDate, receivedAt/effectiveAt и recordedAt. Определить выбор текущей закупочной цены, возвраты и кредит-ноты. Один `ingredient.supplierId` не моделирует нескольких поставщиков; связь должна быть many-to-one через supplier_items, с собственными артикулами/упаковками. |
| Упаковки и количество прихода | **Критический.** «2 коробки × 6 пакетов × 1 kg» прочитано как 2 kg; переменный вес или штучный товар принят как масса. | Хранить исходную строку и отдельно подтверждённые invoice quantity/unit, pricing basis, pack conversion, stock base quantity. Преобразование версионируется и фиксируется в приходе; смена справочника не меняет прошлое. kg↔g допустимо, pc↔g или l↔kg без явного товарного коэффициента — нет. Цена за единицу может иметь больше двух десятичных знаков: разбирать строкой/рационально, не округлять заранее до цента. Отдельно согласовать правила скидок, бесплатного товара, доставки, тары и НДС. |
| Достоверность ИИ | **Высокий.** Модель пропустила строку, неверно поняла единицу или поставщика; суммы сошлись за счёт другой ошибки. | JSON Schema гарантирует форму, а не истинность. Нужны источник/page/fragment для строки, исходное значение рядом с исправленным, неизвестное вместо догадки, сверка полноты/итогов и ручной ввод без ИИ. Непонятные количество/единица/НДС блокируют подтверждение затронутой строки. Отдельный допуск на округление по правилам поставщика; расхождение нельзя «исправить» выдуманной ценой. |
| Цена ИИ и злоупотребление | **Высокий.** Бесплатная регистрация многих ресторанов обходит месячный лимит; параллельные запросы расходуют одну квоту несколько раз; многостраничный PDF стоит намного дороже обычного. | Серверное атомарное резервирование бюджета до вызова; лимиты страниц/байтов/пикселей/токенов, пользователя, ресторана и платформы, ограниченная параллельность и retries, kill switch. Пилот с доступом к OCR по приглашению либо иной антиабьюз-контроль до открытого запуска. Выбор модели — по eval, не Opus по умолчанию. |
| Распознавание как долгий запрос | **Высокий.** Телефон заснул, Edge завершился, статус завис, retry повторно оплачивает запрос. | Durable job в БД с attempt/lease/status, ограниченными повторами и восстановлением; отдельно принятие файла и результат. Не держать транзакцию во время Claude. После неопределённого исхода нельзя обещать ровно один платный вызов; дедупликация снижает риск, резерв расходов его ограничивает. |
| Расход и вложенные заготовки | **Критический для F.** Продажи прошлого месяца списаны по сегодняшнему рецепту; заготовку списали при приготовлении и второй раз при продаже. | Исторические версии блюда и всех reachable preps, POS mapping и версия алгоритма в источнике расхода. Отдельная чистая функция разворачивания количества с portions/output/yield; стоимость для этого не годится. Сначала выбрать модель: сырьё списывается теоретически при продаже **либо** учёт производства и остатка заготовок. Вторая существенно расширяет F. |
| Остатки и пересчёт | **Высокий.** Пустой журнал показывает ложный ноль; во время пересчёта пришёл импорт; поздние продажи до даты пересчёта повторно уменьшили уже посчитанный остаток. | Начальные остатки через инвентаризацию, до неё — неизвестны. Определить effectiveAt, recordedAt, закрытие периода/границу пересчёта и обработку поздних событий. Корректировка — серверная относительно согласованного book balance. Отрицательные остатки и неполнота продаж видимы. |
| POS и повторные импорты | **Высокий.** Пересекающиеся CSV списали продажи дважды; касса даёт оплаты, но не проданные блюда; refund трактуется как возвращённая еда. | Один утверждённый формат/первая реальная касса, стабильные внешние ID либо явные правила замены периодов. Модификаторы, комбо, отмены, возвраты, бизнес-день Europe/Amsterdam/DST и поздние изменения — часть контракта. Финансовый refund не равен физическому возврату на склад. |
| Копии и восстановление | **Критический.** Потеря базы уничтожает и историю; база восстановилась без фото; PITR всего проекта откатил все рестораны вместо одного. | Отдельные проверяемые копии БД и объектов, manifest/checksum и восстановление согласованного набора. Разделить аварийное восстановление проекта и логическое одного ресторана, задать RTO и тренировать restore. |

**Проверенный размер.** Синтетический валидный каталог из 300 ингредиентов, без рецептов/сценариев: 156 цен на ингредиент — **4 525 073 символа**; 1 095 цен — **31 878 773**, сериализатор отказал: `The document is too large (limit 5000000 characters).` Это стресс-сценарии записи каждой закупки/дня, не прогноз частоты изменения цен. Даже еженедельный вариант оставляет мало места для рецептов и baseline-снимков. Лимит 2 000 цен на ингредиент не предотвращает достижение общего лимита раньше.

**Уточнения по платформам.** Service-role доступ действительно обходит RLS, включая Storage; наличие политик не защищает привилегированную ошибку в Edge. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage](https://supabase.com/docs/guides/storage/security/access-control), [Edge auth](https://supabase.com/docs/guides/functions/auth).

У Edge сейчас 256 MB памяти, 2 s CPU на запрос и 150 s idle timeout; платный wall-clock — 400 s. Это дополнительные причины измерить валидацию большого JSON и отделить OCR-job от запроса телефона. [Ограничения Edge](https://supabase.com/docs/guides/functions/limits).

Расценка 3–10 центов за накладную пока не бюджет: нет распределения страниц, output tokens, retries и thinking. На дату проверки Opus 5.5 стоит $4/$20, Sonnet 5.5 — $2/$10 за миллион входных/выходных токенов; PDF учитывает текст и изображение страницы. [Цены Claude](https://platform.claude.com/docs/en/about-claude/pricing), [PDF costing](https://platform.claude.com/docs/en/build-with-claude/pdf-support). Нужны median/p95 стоимости и времени исправления, доля пропусков строк и ошибок единиц на закрытом контрольном наборе. 20–30 накладных подходят для разведки, недостаточны для обещания производственной точности.

## 2. Реальные альтернативы

| Вариант | Плюсы | Минусы и выбор |
|---|---|---|
| Полностью реляционный каталог в том же Supabase: ingredients, price_events, recipe_versions/lines, suppliers; snapshots сценариев отдельно | FK, ограничения удаления, отдельные версии сущностей, короткие записи, меньше конфликтов и естественная историчность. Calc остаётся чистым: получает собранные DTO текущего формата. | Существенная переделка persistence/store, проекции и миграции; контракт полной замены документа нельзя сохранить дословно. Ориентир дополнительного труда 2–4 недели требует прототипа. Предпочтительнее, если E/F и рост — твёрдая цель ближайшего релиза, а не гипотеза. |
| Supabase Auth/Postgres/Storage + свой небольшой Node API/worker вместо всей серверной логики в Edge | Общий JS на поддерживаемом Node, удобнее длинные OCR jobs и обычные транзакции/инструменты диагностики. | Ещё один хостинг, worker lifecycle, пул соединений, обновления, мониторинг; tenant security остаётся нашей задачей. Имеет смысл только если Deno/лимиты подтвердились проблемой. Сам по себе другой провайдер слабости модели не исправит. |

Практический компромисс: C-пилот с документом, но до публичного E — стабильный реестр ingredient IDs/units/archive для связей, реляционная история цен, исторические версии рецептов для F. Не создавать два равноправных источника цен; JSON для существующего calc — проекция. Если такая промежуточная модель сложнее полной нормализации, выбрать первую альтернативу. Много ресторанов само по себе не создаёт общий CAS-конфликт: горячая строка отдельная у каждого ресторана; проблема — работа внутри ресторана и объём его документа.

## 3. Пропущенные требования

- **Смысл склада.** В первом F это расчётные остатки сырья по рецептам с ручными списаниями и пересчётом, а не измеренное потребление. Без партий/сроков годности нельзя обещать прослеживаемость или полноценный склад. Учёт заготовок на полке — отдельное решение, не скрытая часть рекурсивного расчёта.
- **Начало работы.** Создание пустого ресторана без демо; проверенный импорт из браузера/D с предпросмотром; явный момент прекращения независимых записей в старой версии; каталог поставщиков, единицы и начальный пересчёт; первая накладная с помощью, сопоставление первой кассовой выгрузки. Открытый self-service требует дополнительных защиты и поддержки.
- **GDPR.** Нужен договор ресторан ↔ оператор MenuPilot, а не только DPA оператора с Supabase/Anthropic; роли controller/processor для разных данных зафиксировать. Персональные сведения поставщиков/сотрудников, сроки, субпроцессоры, экспорт/исправление/удаление, доступ поддержки и реакция на инцидент — часть продукта. Требование договоров подтверждает [EDPB](https://www.edpb.europa.eu/sme/learn-the-basics/data-controller-or-data-processor_en). Для утечек нужен процесс быстрого уведомления ресторанов; обязанность controller уведомить надзор в применимых случаях — до 72 часов, processor уведомляет controller без неоправданной задержки. [Еврокомиссия](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/obligations_en).
- **EU не означает отсутствие международной обработки.** У Supabase региональны core data/backups, но есть исключения для поддержки, метаданных и CDN; регион Edge надо настроить отдельно. Для Anthropic документировать выбранный endpoint, договор и retention; не обещать ZDR по умолчанию. [Supabase residency](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq), [Anthropic commercial retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data).
- **Архив накладных.** В NL обычный срок хранения счетов — 7 лет, есть исключения; необходимо решить, MenuPilot — юридически значимый архив или рабочая копия с оригиналами в другом месте. Сжатое OCR-изображение не должно автоматически заменять исходник. Удаление аккаунта, ресторана и окончание договора — разные операции; согласовать экспорт, сроки копий и обязанности хранения. [Belastingdienst](https://www.belastingdienst.nl/wps/wcm/connect/bldcontentnl/belastingdienst/zakelijk/btw/administratie_bijhouden/facturen_maken/uw_facturen_bewaren). Это вопросы для договорной проверки перед запуском, не утверждение, что MenuPilot обязан бессрочно хранить всё за клиента.
- **Миграции.** В черновике смешаны версии: сейчас domain `document.version = 1`, storage envelope `schemaVersion = 2`, SQLite `user_version = 2` независимы. Добавление suppliers требует domain migration; envelope bump — только если изменился его контракт. Нужны миграции snapshots/scenarios, совместимость старой D, min supported client, атомарность по tenant и возобновление массовой миграции. Старые клиенты должны отказаться писать новый формат.
- **Эксплуатация.** Владелец сервиса/дежурный, health/alerts по failed jobs, расходам, копиям и росту таблиц; приватные логи без накладных/токенов; ключи/rotation; SMTP delivery/SPF/DKIM, reset-password abuse, восстановление owner; документированный и журналируемый доступ поддержки. Мониторинг деградации одного ресторана и общих лимитов обязателен.
- **Мобильный UX.** Отдельные «Снять фото / Выбрать PDF», поворот/качество/много страниц, прогресс/повтор загрузки, восстановление после сна; на 375 px переключение «оригинал ↔ строка» вместо двух тесных колонок. Проверять реальный iPhone/Safari: Chromium 375 px не проверяет HEIC/камеру. HEIC напрямую не входит в поддерживаемые форматы Claude; нужен проверенный conversion/fallback. [Vision formats](https://platform.claude.com/docs/en/build-with-claude/vision).
- **Оффлайн.** В первом релизе явно online-only подтверждение и запись; показывать отсутствие сети, сохранять безопасный черновик и позволять повтор с тем же opId. Полный offline sync с поздним подтверждением и конфликтами — отдельный этап. Указать, доступны ли рецепты при пропадании сети, как защищён кеш и что происходит при отзыве роли.
- **Форматы и зависимости.** Excel-парсер и HEIC/PDF-обработка отсутствуют в утверждённом списке; нужна отдельная оценка библиотеки/лицензии/безопасности и разрешение. Сначала один CSV-контракт. «Работает с любой кассой» неверно без исходных данных о блюдах и количестве.

## 4. Ответы на семь открытых вопросов

**1. Гибрид или реляционная модель?** Гибрид приемлем как ограниченный переходный этап C, не как доказанная конечная схема C/E/F. Для E нужны стабильные идентификаторы и реляционные price events; для F — версии рецептов. Полная нормализация обоснованна, если она получается проще этого компромисса. До решения — короткий прототип роста, конкурентности и ссылочной целостности, не многонедельная перепись UI.

**2. Общая JS-валидация в Deno?** Реалистична: schema/transitions/calc в изученном графе в основном чистые ES-модули; SQLite/Node HTTP переносить нельзя. Bundle локальных относительных импортов, Web Crypto/ID, BigInt wire encoding и точные версии runtime надо проверить в настоящем Edge. Прогонять общие golden fixtures в Node, Deno и браузере. Не fork валидатора. Проверять и состояние, и переход; серверные часы определяют recordedAt. Предел CPU на больших документах пока не измерен.

**3. Атомарное подтверждение?** Только одна вызываемая сервером функция/транзакция Postgres; последовательные HTTP-запросы Edge транзакцией не становятся.

1. Edge аутентифицирует человека, получает согласованный draft, строит кандидат общими функциями, проверяет схему/переход/эффекты; ИИ здесь уже не вызывается.
2. RPC в одном фиксированном порядке блокирует строки ресторана/документа/накладной, повторно проверяет активную роль и tenant. Повтор того же opId с тем же hash возвращает исходную квитанцию; с другим содержимым — отказ. Бизнес-уникальность confirmed invoice/source movement нужна независимо от opId.
3. Проверяет documentId/revision, draftVersion/hash, неизменность conversion/исходных файлов и допустимый статус. Если исходная ревизия изменилась — ни одной записи, повторный предпросмотр и подтверждение. CAS связывает предварительную JS-проверку с тем состоянием, которое будет записано.
4. Одним commit: документ/price events + history + все stock movements + confirmed invoice + audit + receipt. Нельзя подать произвольный валидированный кандидат в этот RPC из браузера: права вызова только у доверенного серверного пути. Файлы заранее загружены неизменяемо; Storage и Claude не входят в транзакцию Postgres.
5. Тесты: два разных opId подтверждают одну накладную, потерянный ответ после commit, падение на последнем INSERT, изменение черновика/роли/документа между preview и commit. Повторный скан того же счёта ловить также по поставщику/номеру/дате с разбором неоднозначных дублей.

**4. PITR/RPO?** Оставить ≤5 мин для записей БД перед публичным использованием склада, либо получить явное новое решение владельца с честным RPO до суток. История ревизий в той же БД не альтернатива PITR. Сейчас Pro включает 7 дней daily backups, PITR 7 дней стоит около $100/мес дополнительно; официальный пример Small + Pro + PITR — $130/мес до staging/SMTP/ИИ/объектных копий. [PITR billing](https://supabase.com/docs/guides/platform/manage-your-usage/point-in-time-recovery), [backups](https://supabase.com/docs/guides/platform/backups). Для 14–30 дней нужны отдельная retention-схема и стоимость. Файлы Storage не входят в DB backup: для них отдельные RPO/RTO, immutable original и backup manifest. Проверять фактическую восстанавливаемую точку, а не обещать SLA только фактом включения опции.

**5. Без Docker и CI?** Не требовать Docker на компьютере владельца. Разработчик может работать с in-memory/unit и отдельным тестовым Supabase, но перед merge нужны настоящие RLS/SQL/Auth/Storage/Edge-тесты. В CI Linux runner с Docker и Supabase CLI, закреплённые версии и миграции с нуля. Один общий изменяемый staging не использовать для параллельных PR. Если local stack недоступен — выделенный одноразовый облачный стенд/проект с полным reset и секретами только trusted CI; это дороже и не заменяет unit tests. Внешние fork PR не получают секретов. Claude всегда stub в обычном CI, live eval отдельно. Предыдущие local/demo E2E сохранить без сети; cloud integration — отдельная явно разрешённая сетевая группа.

**6. E1 раньше C2?** Разделить C2. Изоляция, права, восстановление, лимиты и минимальная мобильная работа — обязательная часть C до чужих данных. После этого E1 можно делать до остальной полировки совместной работы/UX. Ускорять пилот загрузки телефона разумно; выпускать архив без надёжности и tenant tests — нет. Взять реальные накладные и образец POS CSV для исследования можно ещё раньше.

**7. Что переиспользовать из D?** `createRemoteAdapter`, CAS documentId/revision, hash/opId/receipt, ошибки, publish-after-success, общие price/schema/transitions/calc, последствия D5, состояния stale/expired/applied, защиту черновиков и контрактные fixtures. Не переносить Node SQLite/backup/lock, локальные токены ui/cli и polling как облачную стратегию без расчёта нагрузки. В `remoteAdapter` polling каждые 2 s; в облаке нужен backoff/visibility/realtime с последующей сверкой revision. D5 — один add-price в одной SQLite-транзакции, E — пакет строк и отдельный stock ledger. Локальный restore/reset и ограниченное хранение квитанций не подходят напрямую: invoice/source uniqueness должны переживать повторные импорты и старые retries. Существующий adapter contract расширить cloud-specific правилами, а не разрешать опасный restore ради дословного совпадения.

## 5. Сроки и стоимость

Это оценка инженерного труда с проверкой и исправлениями, не гарантия скорости агентов. Таблица Opus даёт 27–39 рабочих дней без C0 уже по собственной арифметике; назвать это всем объёмом за 1–1,5 месяца слишком оптимистично. Наиболее недооценены C2, F2 и F3; независимые проверки не устраняют последовательных зависимостей.

| Этап | Реалистичный ориентир, человеко-дни |
|---|---:|
| C1: auth, роли, tenant isolation, write/CAS, bootstrap | 10–16 |
| C2: совместная работа, безопасный import/restore, эксплуатация/копии, mobile | 8–12 |
| E1: поставщики, версии упаковок, надёжная загрузка/архив | 5–8 |
| E2: OCR jobs, review, атомарное подтверждение, eval | 10–16 |
| F1: ledger, начальный пересчёт, корректировки и время | 8–12 |
| F2: один подтверждённый CSV-формат и исторический расход | 7–12 |
| F3: одна документированная POS-интеграция с доступом | 10–20 + ожидание |

C–F2: **48–76 человеко-дней**; F3 отдельно. C0 — не обещать один день: учётные записи можно завести быстро, договоры/SMTP/материал пилота/доступ кассы зависят от внешних сторон. Для ограниченного пилота C–F2 ориентир **8–12 календарных недель** при выделенной реализации и ревью, затем наблюдение реальных поставок/продаж; открытый self-service с поддержкой может занять **3–4 месяца и более**. Полная нормализация может добавить труд по persistence, но часть его заменяет работы по сложной защите гибрида — не суммировать всё механически.

Расходы считать на сервис и на ресторан: prod + staging compute, PITR, хранение/egress оригиналов и независимых копий, SMTP, ИИ/retries, наблюдаемость и поддержка. $25 — базовый тариф, не общий бюджет. [Supabase pricing](https://supabase.com/pricing). Для OCR сначала получить стоимость и долю ручных исправлений на настоящем наборе; модель менять только после повторного eval.

Выбор POS отложить до образца реального отчёта. Нидерланды отсутствуют в списке регионов Square card processing; это **не** означает полного отсутствия Square APIs, но делает совет «начать со Square» без первого клиента слабым. [Square international development](https://developer.squareup.com/docs/international-development). SumUp имеет transaction API и поля products, однако это не доказывает полноту блюд/модификаторов всех оплат конкретной ресторанной кассы; необходим sample и сверка итогов. [SumUp Transactions](https://developer.sumup.com/api/transactions).

## 6. Условия принятия

1. До C: зафиксировать tenant boundary, серверные команды и правила import/restore, domain/envelope migration, RPO/RTO и реальную ежемесячную смету.
2. До E: доказать атомарное и идемпотентное подтверждение; решить registry/историю цен/рост; подтвердить упаковки, источники дат и correction flow; durable OCR jobs с бюджетом и контрольным набором.
3. До F: определить расчётный характер сырьевых остатков, начальный пересчёт, неизменяемые версии рецептов, количество/yield/округление и один контракт POS. Функция quantities должна работать даже при неизвестной цене ингредиента.
4. До открытой регистрации: тесты изоляции всех путей, restore drill БД+файлов, договоры/retention, антиабьюз ИИ и сценарии поддержки. Ранний пилот с несколькими приглашёнными ресторанами допустим при выполнении их границ безопасности.

## 7. Существенные разногласия с Opus

- **Один растущий документ как основа всего C/E/F.** Возражение основано на измеренном размере и отсутствии FK/исторических рецептов, а не на предпочтении SQL. Переиспользование UI не оправдывает сохранение всех прежних write semantics.
- **Ежедневная копия + свои ревизии как альтернатива RPO ≤5 мин.** Это другое обещание сохранности; нельзя незаметно подменить требование. Также нужен отдельный backup файлов.
- **Существующий CAS + recipe merge как достаточная совместная работа.** Merge сейчас касается полей черновика одного рецепта; `lines` неделимы. Он не объединяет накладные, цены, удаления и историю всего ресторана.
- **«Продажи × рецепт» как достаточное описание складского расхода.** Без исторических версий, portions, yield, поздних событий, возвратов и решения по производству заготовок это даёт неверные остатки.
- **CSV/Excel для любой кассы и F2 за 3–4 дня.** Произвольная выгрузка не гарантирует нужные данные; импорт — это также дедупликация, временные периоды и исправления, не только парсер.
- **Opus по умолчанию и 3–10 центов как ориентир бюджета.** Нужны измерения точности и полной стоимости; более дорогая модель не гарантирует обнаружение пропущенной строки/неверной упаковки. Лимит на ресторан обходится массовой регистрацией.
- **Общий срок 1–1,5 месяца, C2 за 3–5 и F3 за 3–5 дней.** Для прототипа допустимо; для многих ресторанов с надёжным учётом и поддержкой не принимаю.

С Supabase как первой платформой, чистым BigInt calc, явным подтверждением человеком, отсутствием автоматического изменения рецептов и порядком C → E → F существенных возражений нет.
