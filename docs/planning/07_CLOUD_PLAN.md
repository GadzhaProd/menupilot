## A. Обязательные изменения после критики Sol (приняты координатором)

Критика: «принять с изменениями». Supabase, общий BigInt calc, подтверждение человеком и порядок
C → E → F — без возражений. Изменения:

1. **Модель хранения.** Один документ каталога на ресторан не годится как основа C/E/F: синтетический
   каталог 300 ингредиентов × 156 цен (еженедельно 3 года) = 4 525 073 символа при лимите сериализатора
   5 000 000, без рецептов и сценариев. Для облака — реляционный каталог (ingredients, price_events,
   suppliers, supplier_items, recipe_versions/lines, сценарии отдельно) с FK и ограничениями удаления;
   `src/calc/` получает собранный DTO текущего формата. Один авторитетный источник цен. Перед C1 —
   короткий прототип роста, конкурентности и ссылочной целостности.
2. **Сервер не обходит изоляцию.** service role обходит RLS (включая Storage): каждая привилегированная
   операция повторно проверяет актуальное членство и принадлежность всех ID ресторану; составные FK
   `(restaurant_id, id)`; прямые REST-записи в обход валидатора запрещены; RPC с ограниченным EXECUTE и
   закреплённым search_path. Тесты изоляции всех путей: REST, RPC, Edge, Storage list/signed URL.
3. **Роли и приглашения** меняет только сервер; приглашение одноразовое, привязано к ресторану, роли и
   подтверждённому email; передача владения, запрет потери последнего owner, отзыв доступа; роль
   проверяется в момент commit.
4. **Storage:** приватный bucket, политики на каждую операцию, серверные имена, неизменяемые файлы с
   hash, короткие signed URL; черновики/кеш разделены по user + restaurant + documentId.
5. **Подтверждение накладной — одна транзакция Postgres** (цены + история + все движения склада +
   статус + аудит + квитанция). opId с hash содержимого **и** бизнес-уникальность прихода по
   invoice/line и по поставщику/номеру/дате. Если ревизия/черновик/роль изменились — ни одной записи,
   новый предпросмотр. Тесты: два opId, потерянный ответ, падение последнего INSERT, изменения между
   preview и commit.
6. **Проверять переход, а не только состояние:** на сервере `assertValidDocument` + `assertValidTransition`
   + связи с журналами. Import/reset/restore не переносить из D дословно: при наличии журналов —
   компенсирующие записи, отдельный согласованный restore.
7. **Совместная работа:** CAS предотвращает потерю, но не разрешает конфликт; у черновика накладной своя
   версия; при изменении последствий цены — повторный предпросмотр.
8. **Даты цен:** invoiceDate, effectiveAt и recordedAt раздельно; правила текущей закупочной цены при
   нескольких поставщиках; возвраты и кредит-ноты.
9. **Упаковки:** хранить исходную строку и отдельно подтверждённые количество/единицу, базу цены,
   коэффициент упаковки (версионируется) и количество в базовых единицах; pc↔g или l↔kg только с явным
   коэффициентом товара; цену за единицу разбирать строкой без раннего округления; скидки, бесплатный
   товар, доставка, тара, НДС — явные правила. Неясная строка блокирует подтверждение.
10. **ИИ:** схема гарантирует форму, не истинность — источник (страница/фрагмент) для строки, «неизвестно»
    вместо догадки, сверка итогов, ручной ввод без ИИ. Durable OCR job (attempt/lease/status), без
    транзакции во время вызова. Атомарное резервирование бюджета до вызова, лимиты страниц/байт/
    пикселей/токенов на пользователя, ресторан и платформу, kill switch, пилот по приглашению. Модель
    выбирать по eval (median/p95 стоимости, пропуски строк, ошибки единиц), не Opus по умолчанию.
    HEIC не поддерживается Claude напрямую — проверенная конвертация.
11. **Склад:** в F1 это расчётные остатки сырья с ручными списаниями и пересчётом; до первой
    инвентаризации остаток «неизвестен», а не ноль; effectiveAt/recordedAt, граница пересчёта, поздние
    события, отрицательные остатки видимы. Расход по продажам — по историческим версиям блюда и всех
    reachable preps; отдельная чистая функция количеств (работает и при неизвестной цене).
12. **POS:** один подтверждённый формат первой реальной кассы, стабильные внешние ID, правила замены
    периодов; модификаторы, комбо, отмены, возвраты (финансовый refund ≠ возврат на склад), бизнес-день
    Europe/Amsterdam/DST. «CSV с любой кассы» не гарантирует нужных данных.
13. **Копии:** история ревизий в той же БД не заменяет PITR; файлы Storage копируются отдельно
    (manifest/checksum); разделить аварийное восстановление проекта и логическое одного ресторана;
    задать RTO и тренировать restore.
14. **Юридическое и эксплуатация:** договор ресторан ↔ оператор (GDPR, роли controller/processor),
    субпроцессоры, процесс уведомления об инцидентах; Supabase EU не исключает международной обработки
    (поддержка, CDN, регион Edge); retention Anthropic; срок хранения счетов в NL обычно 7 лет — решить,
    является ли MenuPilot юридическим архивом. Мониторинг, алерты расходов/ошибок, SMTP с SPF/DKIM,
    журналируемый доступ поддержки.
15. **Тесты/CI:** Docker на компьютере владельца не требуется; перед merge — настоящие RLS/SQL/Auth/
    Storage/Edge-тесты в CI (Linux + Docker + Supabase CLI) или одноразовый облачный стенд; Claude в CI
    всегда заглушка, live eval отдельно и с одобрения.
16. **Разделить C2:** изоляция, права, восстановление, лимиты и минимальная мобильная работа обязательны
    до чужих данных; после этого E1 можно раньше остальной полировки.

## C. Исходный черновик (Opus, 2026-10-23) — заменяется разделом A там, где они расходятся

### 1. Решения владельца (2026-10-23)

1. Облачная версия **для многих ресторанов**: каждый ресторан регистрируется сам, данные ресторанов строго разделены. Оплата/подписки — позже, но архитектура должна их допускать.
2. Пользователи ресторана: **владелец** и **управляющий**. Оба могут подтверждать новые цены.
3. Фото/PDF накладной загружается **с телефона** (пересылка на компьютер отвергнута как неудобная).
4. Накладную распознаёт **встроенный облачный ИИ** (Claude API), а не агент разработчика. Человек всегда подтверждает результат.
5. Склад: журнал прихода по накладным **+ остатки + списания**. Расход продуктов — **из кассы (POS)**. Какая касса — неизвестно.
6. Порядок: **сначала облачная версия**, затем накладные, затем склад.

Ранее утверждённое, что сохраняется: деньги — целые центы, промежуточные — микро-евро в BigInt, все формулы в `src/calc/` (чистые функции), цены без НДС, «Contribution», «Recipe-based ingredient cost», неизвестное ≠ ноль, история цен только дописывается, симулятор не меняет реальные данные, UI EN+NL, React 19 + TS + Tailwind v4 + shadcn. Веб-демо (GitHub Pages, браузерное хранилище) остаётся. Локальная версия D остаётся в режиме поддержки (без новых функций).

### 2. Что меняется в рамках проекта (нужно одобрение и правка AGENTS.md)

Из списка «вне рамок» выходят: auth, AI features, invoices/OCR, inventory, POS. Остаются вне рамок: billing (пока), multi-location внутри одного ресторана, новые валюты, аналитика сверх описанной, аллергены.

### 3. Предлагаемая архитектура

### 3.1 Платформа
- **Supabase, регион EU (Frankfurt)**: Auth (email+пароль, ссылка-приглашение), Postgres с RLS, Storage (приватный bucket), Edge Functions (Deno/TS) для серверной логики и вызова Claude API с секретным ключом.
- Тариф: Pro ($25/мес) для продакшена (Free засыпает через 7 дней без активности). Отдельный проект для staging.
- Фронтенд — тот же Vite/React SPA, отдельная сборка `cloud` (статический хостинг; GitHub Pages или аналог, свой домен желателен).
- Новые зависимости (нужно одобрение): `@supabase/supabase-js` (клиент), в Edge Functions — `@anthropic-ai/sdk` (точные версии).

### 3.2 Модель данных — гибрид «документ + журналы»
- **Каталог ресторана** (ингредиенты с историей цен, рецепты/заготовки, сценарии) остаётся **одним документом** в формате текущего `schemaVersion`, по одной строке на ресторан: `restaurant_documents(restaurant_id, document jsonb, document_id, revision, updated_at, updated_by)`. Запись — только через Edge Function `write`: проверка членства и роли → общая валидация `src/store/schema.js` (тот же JS-код в Deno) → CAS по `revision` + квитанция `opId` в одной транзакции (Postgres-функция / `SELECT … FOR UPDATE`). Клиент: новый `cloudAdapter` поверх существующего `createRemoteAdapter` (контракт `storageAdapterContract` уже есть). Конфликты двух пользователей — существующий CAS + 3-way merge рецептов.
  - Почему так: переиспользуем store, валидацию, расчёты, merge и весь UI; не переписываем модель на таблицы.
  - Риск: документ растёт с историей цен; для ресторана на ~300 ингредиентов и годы истории — оценить размер; бюджет как в D (лимиты).
- **Журналы (высокий объём, только дописываются)** — отдельные реляционные таблицы с `restaurant_id` и RLS: `invoices`, `invoice_files`, `invoice_lines`, `supplier_items` (как товар называется у поставщика → наш ингредиент + коэффициент упаковки), `stock_movements` (приход/списание/расход по продажам/корректировка пересчёта), `sales_imports`, `audit_log`.
- **Поставщики**: в документе (как ингредиенты) — `suppliers[]`, у ингредиента — необязательный `supplierId`. Изменение формата документа → bump `schemaVersion` + тестируемый шаг миграции (общий для браузера, D и облака).
- Связь журналов с документом: `stock_movements` ссылаются на ingredient id документа; удаление ингредиента, на который ссылаются движения, запрещено (как уже запрещено для рецептов).

### 3.3 Арендаторы, роли, изоляция
- Таблицы `restaurants`, `memberships(user_id, restaurant_id, role: owner|manager)`, `invitations(email, role, token hash, expires_at)`.
- RLS на **каждой** таблице и в Storage (путь `restaurant_id/...`) по членству. Сервисный ключ — только в Edge Functions.
- Права: owner — всё, включая приглашения, удаление ресторана, экспорт. Manager — каталог, поставщики, накладные, подтверждение цен, склад; не может приглашать/удалять ресторан.
- Обязательные тесты изоляции: пользователь ресторана A не читает/не пишет/не видит файлы ресторана B ни через REST, ни через Storage, ни через Edge Functions.
- `audit_log`: кто и когда изменил цену/подтвердил накладную/списал.

### 3.4 Накладные и распознавание
- Телефон: страница «Загрузить накладную» с `<input type=file accept="image/*,application/pdf" capture>` (камера), несколько фото на одну накладную, PDF. Клиент уменьшает фото (длинная сторона ~2000 px, JPEG) перед загрузкой. HEIC с iPhone — проверить конверсию.
- Edge Function `recognize`: берёт файлы из Storage → Claude API (модель Opus 5.5 по умолчанию; вариант дешевле — Sonnet 5.5, решить по замеру точности) со **структурированным выводом** (JSON Schema): поставщик (название, KvK/BTW если есть), номер и дата накладной, строки (название у поставщика, артикул, количество, единица/упаковка, цена за единицу excl. VAT, ставка НДС, сумма), итоги. Результат проверяется на сервере (схема + арифметика строк/итогов в целых центах), сохраняется как **черновик** `invoices.status = 'draft'`. Ничего не применяется автоматически.
- Сопоставление: поставщик → `suppliers` по названию/KvK; строки → `supplier_items` (запоминаем выбор пользователя); новые строки пользователь сопоставляет вручную один раз.
- Экран проверки: фото рядом со строками; по каждой строке — «цена не изменилась» / «изменилась: было → стало (×N)» / «новый товар»; предупреждения (×3, ноль, НДС непонятен, суммы не сходятся).
- Подтверждение (owner или manager): в одной операции — новые цены в историю (append-only, через тот же CAS документа), приход в `stock_movements`, накладная `confirmed`. Отклонение — `rejected`, ничего не меняется.
- Стоимость ИИ: оценка 3–10 центов за накладную (замерить). Платит платформа → лимит распознаваний на ресторан в месяц, кнопка повторного распознавания ограничена. Ключ Anthropic только в секрете Edge Function; лимит расходов в консоли Anthropic.
- Безопасность ИИ: текст на фото — недоверенные данные; модель только заполняет схему, у неё нет инструментов; любые значения проверяются и подтверждаются человеком.

### 3.5 Склад
- `stock_movements(restaurant_id, ingredient_id, qty_milli BIGINT signed, kind: receipt|waste|sale|count_adjust, source_ref, at, by)`. Остаток = сумма движений (материализованный итог по желанию).
- Списание: ингредиент, количество, причина (порча, проба, ошибка…). Не трогает рецепты (пищевая безопасность — не наша рекомендация).
- Пересчёт (инвентаризация): вводим фактический остаток → корректирующее движение → видно расхождение «по учёту vs факт».
- Расход по продажам: продажи блюд × рецепт (с вложенными заготовками и yield) → расход ингредиентов в базовых единицах; формулы в `src/calc/` (BigInt, правила округления 03).
- Касса: **этап F2 — импорт отчёта продаж из кассы (CSV/Excel)** — работает с любой кассой без API; сопоставление «позиция кассы → блюдо» запоминается. **Этап F3 — прямое подключение** первой кассы (выбрать по клиентам: Square/SumUp — открытый API; Lightspeed — партнёрская программа; агрегатор Chift — цены по запросу).

### 3.6 Надёжность и данные
- Ранее утверждённая цель для C: RPO ≤ 5 мин (PITR) + ежедневные копии 14–30 дней + история ревизий. PITR в Supabase — платное дополнение: подтвердить стоимость; альтернатива — ежедневные копии Pro + собственная история ревизий документа + журналы только дописываются.
- Экспорт данных ресторана (документ + журналы + файлы) и удаление аккаунта/ресторана (GDPR). Политика конфиденциальности, DPA с Supabase и Anthropic (действия владельца).
- Письма (приглашения, сброс пароля): SMTP-провайдер для продакшена.

### 3.7 Тесты
- Core/UI — как сейчас. Облако: локальный Supabase (CLI + Docker) для интеграционных тестов RLS/Edge Functions; в CI — тот же стек. **На машине владельца сейчас нет Docker** — нужна установка (Docker Desktop/OrbStack) или облачный staging-проект для тестов.
- Claude API в тестах — заглушка. Отдельный ручной eval на 20–30 реальных/синтетических накладных (стоит денег, запуск с одобрения).
- E2E (Playwright) против staging, без внешних запросов кроме своего стенда.

### 5. Открытые вопросы для критики
1. Гибрид «документ каталога + реляционные журналы» vs полностью реляционная модель сразу (учитывая многопользовательскую работу и рост истории цен).
2. Общая валидация JS в Edge Functions (Deno) — реалистично ли без расхождений с браузером/Node.
3. Где проходит граница транзакции при подтверждении накладной: цены живут в документе (CAS), приход — в таблице. Нужна одна атомарная операция.
4. PITR/RPO: оставить цель ≤5 мин (стоимость) или пересмотреть.
5. Тесты без Docker; CI.
6. Порядок этапов: не выгоднее ли E1 (загрузка с телефона) делать раньше C2.
7. Что из локальной версии D переиспользовать (план-подтверждение, предупреждения).
