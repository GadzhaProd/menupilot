# 03. Архитектура MenuPilot (MVP)

Статус: **архитектура MVP v1 утверждена владельцем.**

## 1. Главное решение
MenuPilot v1 — это **статическое браузерное приложение без сервера**. Данные хранятся в браузере пользователя (`localStorage`), есть экспорт и импорт JSON для резервной копии. Публичное демо размещается бесплатно на GitHub Pages.

Почему не сервер с базой:
- **Публичное демо обязательно.** Общая база на сервере означала бы, что все посетители редактируют одни и те же данные. Пришлось бы делать изоляцию, постоянный диск и платный хостинг.
- **Объём данных маленький:** десятки ингредиентов и блюд. Сервер добавил бы маршруты API, двойную валидацию, хостинг и сопровождение без пользы для MVP.
- Это осознанная простота, а не ограничение: переход на сервер позже затронет только модуль хранения (раздел 4).

Чем жертвуем: данные привязаны к одному браузеру и устройству. Если очистить данные сайта, они пропадут. Смягчение: кнопка «Export backup», предупреждение в интерфейсе и импорт.

## 2. Стек
| Слой | Выбор | Почему |
|---|---|---|
| UI и сборка | Vite + React 19 + TypeScript (`strict`) + Tailwind CSS v4 + shadcn/ui | Статическая сборка для GitHub Pages; алиас `@` → `src` |
| Ядро | `src/calc/` и `src/store/` — JavaScript + JSDoc | Существующее поведение расчётов и хранилища сохраняется |
| Хранение | `localStorage`, ключ `menupilot:v1`, версия формата | Хватает для малых данных, сохраняется между перезапусками |
| Расчёты | `src/calc/` — чистые функции, `BigInt` | Точность и детерминизм |
| Типовая граница | `src/ui/domain/*.ts`, readonly-типы документа, результатов и store | UI получает проверенные типы без переписывания ядра |
| Тесты | `node:test` для core; Vitest + jsdom + Testing Library для UI | Раздельные команды и общий `npm test` |
| Деплой | GitHub Actions → GitHub Pages | Production base `/menupilot/` |

Зависимости фиксируются точными версиями в `package.json` и lockfile. Допустимые пакеты перечислены в `AGENTS.md`; новые зависимости вне списка требуют одобрения координатора.

## 3. Схема
```
 Браузер
 ┌──────────────────────────────────────────────────────────┐
 │  React UI (src/ui/)                                        │
 │  Dashboard · Ingredients · Recipe · Profit Simulator      │
 │        │ типизированный адаптер              │             │
 │        ▼                                     ▼             │
 │  Store (src/store/, JS)              Calc (src/calc/, JS) │
 │  валидация, версия, экспорт/импорт  чистые функции, BigInt │
 │        │                                                  │
 │        ▼                                                  │
 │  localStorage  "menupilot:v1"  (JSON)                     │
 └──────────────────────────────────────────────────────────┘
```
Правила зависимостей: `calc` ни от чего не зависит; `store` использует только валидацию; React UI обращается к `store` через тонкую границу `src/ui/domain/*.ts`, а к `calc` — для производных значений. Формулы существуют **только** в `calc`.

### Контракт UI ↔ store
Store — единственный источник истины. Команда UI вызывает метод store вне reducer; при успехе отправляет `dispatch({ type: 'documentReplaced', document })`, при ошибке показывает сообщение и оставляет документ на экране прежним. Reducer чистый и безопасен при повторном вызове React StrictMode. Черновики форм живут в локальном состоянии компонентов. Результаты `calc` с полями `BigInt` вычисляются как производные (`useMemo`), не сохраняются и не сериализуются. В JSON/localStorage находятся только документ, baseline и overrides с безопасными целыми. Деньги показываются существующими форматтерами, без преобразования `BigInt` в `Number`.

## 5. Данные (документ в localStorage)
```js
{
  version: 1,
  settings: { defaultVatRateBp: 900 },             // 9,00% — ставка по умолчанию, изменяемая
  ingredients: [{
    id, name,
    unit: "g" | "ml" | "pc",                        // базовая единица; kg/l переводятся при вводе
    prices: [{                                      // append-only история
      seq,                                          // порядковый номер записи (возрастает)
      recordedAt,                                   // момент, с которого действует цена (не будущее; см. «Дата цены» ниже)
      packPriceCents,                               // цена упаковки БЕЗ НДС, целое
      packSizeMilli                                 // размер упаковки на момент цены (снимок), целое ×1000
    }]
  }],
  recipes: [{
    id, name, kind: "dish" | "prep",
    // dish: цена и ставка НДС, число порций партии, optional monthlyVolume
    menuPriceInclVatCents, vatRateBp, portions, monthlyVolume,
    // prep: только выход партии; dish-поля отсутствуют
    outputMilli, outputUnit: "g" | "ml" | "pc",
    lines: [{ id, ref: { kind: "ingredient" | "prep", id }, netQtyMilli, yieldBp }]
  }],
  scenarios: [{
    id, recipeId, name, createdAt,
    baseline: { /* снимок рецепта и цен на момент создания */ },
    overrides: { menuPriceInclVatCents?, monthlyVolume?, ingredientPriceCents: {ingredientId: cents}, lineQtyMilli: {lineId: milli} }
  }]
}
```
Все числа в хранилище — безопасные целые (`Number.isSafeInteger`); `monthlyVolume` необязателен, целое ≥ 0, оценка владельца, не прогноз. `BigInt` используется только внутри `calc`. Ввод разбирается из строки без `parseFloat`: деньги — до 2 знаков; количества в g/ml/pc — до 2 знаков, в kg/l — до 3 (разделители тысяч не поддерживаются). Даты (`recordedAt`, дата сравнения) — полный ISO-момент с часовым поясом.

**Дата цены («Price valid from»).** `recordedAt` — это момент, **с которого действует цена**, а не «когда нажали Save». Формат данных не менялся (версия 1). Владелец может указать дату накладной (календарный день в UTC, как и даты сравнения на Dashboard): `store.addPrice(id, price, { effectiveDate: 'YYYY-MM-DD' })` и `store.addIngredient({ …, price, effectiveDate })`. Правила (`src/store/price.js`):
- без `effectiveDate` или для сегодняшнего дня (UTC) `recordedAt` = текущий момент, как раньше;
- прошлый день D → `recordedAt = D T00:00:00.000Z`. Dashboard сравнивает на конец дня (`D T23:59:59.999Z`), поэтому цена с датой D действует при сравнении на D и позже, но не на D−1. Выбор цены остаётся «последняя запись с `recordedAt` ≤ даты сравнения, при равенстве — больший `seq`» (`src/calc/internal.js`); часовой пояс компьютера не участвует;
- история остаётся неубывающей по `recordedAt` и append-only, текущая цена — последняя запись: день D не может быть раньше (UTC-дня) предыдущей цены; в тот же день используется момент предыдущей записи (побеждает больший `seq`);
- D не в будущем: допускается день, который уже наступил в каком-либо часовом поясе (не позже UTC-даты `now + 14 ч`), он записывается как «сейчас»; дальше — ошибка `invalid`. Окно `FUTURE_TOLERANCE_MS` для самого `recordedAt` не меняется;
- предложения агента (локальная версия, `server/plans.js`) `effectiveDate` не передают и по-прежнему ставят «сейчас».
В UI поле необязательное (по умолчанию сегодня), цена `0` требует отдельного подтверждения (галочка), пустая цена — «cost unknown». Идентификаторы строк, сущностей и ссылки уникальны. У строки рецепта нет своей единицы: `netQtyMilli` всегда в базовой единице ссылки (ингредиента или `outputUnit` заготовки); UI переводит kg→g и l→ml при вводе. Prep не имеет меню, НДС, порций или объёма продаж.

## 6. Расчёты и округление (контракт)
Единицы: деньги внутри расчётов — **микроевро** (µ€, 1 € = 1 000 000 µ€, 1 цент = 10 000 µ€). Количества — тысячные доли базовой единицы. Все операции выполняются на `BigInt`. Единственная операция округления — `roundDiv(a, b)`: деление с округлением **half away from zero**, одинаково для положительных и отрицательных чисел.

| Шаг | Формула | Округление |
|---|---|---|
| 1a. Строка ингредиента (µ€) | `roundDiv(BigInt(packPriceCents)·10⁴ · netQtyMilli · 10⁴, packSizeMilli · yieldBp)` | до 1 µ€ |
| 1b. Строка заготовки (µ€) | `roundDiv(batchCostµ(prep) · netQtyMilli · 10⁴, outputMilli · yieldBp)` | до 1 µ€ |
| 2. Стоимость партии | Σ строк | точная сумма |
| 3. Себестоимость порции | партия / portions | roundDiv до 1 µ€ |
| 4. Цена без НДС | menuPriceInclVatCents·10⁴ · 10⁴ / (10⁴ + vatRateBp) | roundDiv до 1 µ€ (в центы **не** округляется) |
| 5. Contribution за порцию | цена без НДС − себестоимость порции | точная разность, может быть отрицательной |
| 6. Food cost %, margin % | себестоимость (или contribution) / цена без НДС | roundDiv до 0,1%; при цене 0 — «n/a» |
| 7. Месячный contribution | contribution µ€ · monthlyVolume / 10⁴ | roundDiv до цента, один раз |
| 8. Отображение суммы | µ€ / 10⁴ | roundDiv до цента |
| 9. Разница «сценарий − baseline» | разность **отображаемых** (уже округлённых) значений | — |
| 10. Monthly impact at your volume | месячный contribution (шаг 7) по текущим ценам − месячный contribution (шаг 7) по ценам на дату сравнения; блюдо без объёма — «—», не входит в итог меню; итог меню — сумма этих разностей | по правилу 9; та же формула, что разница месячных значений в симуляторе |

Пояснения:
- Ошибка округления строки не превышает 0,5 µ€, то есть в 20 000 раз меньше цента. Поэтому разбиение одного ингредиента на две строки не может изменить отображаемый результат на практике. Политика зафиксирована явно.
- Правило 9 выбрано ради предсказуемости (POLA): числа в таблице сравнения всегда сходятся «на глаз».
- **Неизвестное ≠ ноль.** Если у ингредиента нет цены, стоимость строки неизвестна. Тогда себестоимость блюда показывается как «cost unknown», и все производные значения тоже.
- Выход (yield) применяется только к своей строке, а ко всему рецепту — никогда.
- Килограммы и литры переводятся в g/ml при вводе. Перевод массы в объём и обратно запрещён; количество строки хранится в базовой единице того, на что она ссылается.
- Стоимость упаковки хранится как введённые `packPriceCents` и `packSizeMilli`; `packUnitPriceDisplay` преобразует для UI только представление к kg/l/pc. Например, 1 kg за €11,20 → €11.20/kg; 250 g за €2,80 → €11.20/kg. Данные не меняются.
- Для списка заготовок `prepUnitCostDisplay` показывает стоимость batch за kg/l/pc: для outputUnit g или ml нормирует `batchCostµ × 1 000 000 / outputMilli` к kg/l, для pc — `batchCostµ × 1 000 / outputMilli` к штуке; отображаемая сумма округляется до цента через `roundDiv`.
- Рекурсивный `batchCostµ(prep, asOf, overrides)` суммирует строки заготовки теми же формулами. Делить партию заготовки на порции не нужно: строка блюда берёт количество заготовки как долю от полного `outputMilli`. Unknown распространяется вверх; дата цен `asOf` и override цены ингредиента общие на всех уровнях. Цикл отклоняется при сохранении и импорте, максимальная глубина — 5 уровней; используемые ingredient/prep удалить нельзя. Симулятор меняет цены ингредиентов через всю рекурсию, а `lineQtyMilli` — только строки блюда верхнего уровня. Baseline snapshot содержит рецепт блюда, все достижимые заготовки и цены.
- Подсказка food cost «NL horeca average ≈ 30% (Sligro, 2025)» необязательна и справочная, не норма/цель ([Sligro](https://www.sligro.nl/inspiratie/rendement-kosten/kengetallen.html)). НДС: [Belastingdienst](https://www.belastingdienst.nl/wps/wcm/connect/bldcontentnl/belastingdienst/zakelijk/btw/btw_berekenen_aan_uw_klanten/btw_berekenen/btw_tarief/btw_tarief); цены потребителю с НДС: [ACM](https://www.acm.nl/nl/verkoop-aan-consumenten/consumenten-informeren/prijzen-vermelden).

Ручной пример (также тест): заготовка соуса даёт 1 kg (`outputUnit=g`, `outputMilli=1 000 000`). В ней 800 g томатов по €2,00/kg: `roundDiv(2 000 000 µ€ × 800 000 × 10⁴, 1 000 000 × 10⁴) = 1 600 000 µ€`; 20 g специй по €10,00/kg стоят `roundDiv(10 000 000 × 20 000 × 10⁴, 1 000 000 × 10⁴) = 200 000 µ€`. `batchCostµ=1 800 000 µ€` (€1,80). Блюдо использует 150 g соуса, выход 100%: `roundDiv(1 800 000 × 150 000 × 10⁴, 1 000 000 × 10⁴)=270 000 µ€` = €0,27. Сумма строк партии точная; округляется только каждая строка по `roundDiv`.

Контрольный пример из ТЗ (будущий тест): цена в меню €13,08 с НДС 9% → €12,00 без НДС. Себестоимость €4,20 → €4,85, contribution €7,80 → €7,15, разница −€0,65. При 300 порциях: €2 340,00 → €2 145,00, разница −€195,00.

## 7. Поток данных
1. **Изменение реальной цены:** в Ingredients пользователь вводит новую цену. `store` дописывает запись в `prices` (старая сохраняется) и сохраняет документ. Dashboard пересчитывает себестоимость через `calc`.
2. **Dashboard:** для каждого блюда и его заготовок считается себестоимость по текущим ценам и по ценам на дату сравнения (по умолчанию 30 дней назад, пользователь может изменить). Состав рецепта в обоих случаях текущий. “Monthly impact at your volume” — разность месячных contribution по шагу 10 (03 §6); в итог входят только блюда с `monthlyVolume`.
3. **Симулятор:** создаётся сценарий со **снимком** baseline. `simulate(snapshot, overrides)` возвращает новые показатели и ничего не меняет: входные данные заморожены, и тест проверяет, что документ не изменился. Сценарии сохраняются в `scenarios`. Если реальный рецепт или цены изменились после создания сценария, показывается пометка «Baseline changed — update?».
4. **Импорт:** файл проверяется по схеме и версии, включая циклы, глубину и совместимость единиц. При любой ошибке текущие данные остаются нетронутыми.

### Несколько вкладок

Браузерный адаптер проверяет ревизию, точное совпадение `menupilot:v1` с исходным
сырым текстом и `menupilot:revision`. Числовая ревизия и протокол миграции описаны
ниже, в разделе «Слой хранения и ревизии». Восстановление A после B — новая запись,
поэтому вкладка со старой A должна выполнить Load latest перед сохранением.

`BrowserStorageAdapter` берёт исключительный Web Lock `menupilot:document-writer`
на время одной операции: CAS → история → новый номер → основной документ.
Внутри критической секции между сравнением и записью нет `await`. Ожидание очереди
асинхронно: кнопка показывает сохранение и не принимает повторные нажатия.
Нет заранее захваченного права у активной вкладки или передачи через BroadcastChannel.
При отсутствии Web Locks действует режим без записи; чтение/экспорт доступны.
Через 5 секунд ожидание отменяется через AbortSignal и возвращает write-busy.
Таймаут не выдаёт права писать; форму можно закрыть или повторить сохранение.
Старый клиент с длительным lease следует перезагрузить.

При несовпадении исходных данных **любая** запись (включая импорт и сброс)
отклоняется. UI предлагает «Load latest data / Nieuwste gegevens laden», сохраняя
локальные поля. Автоматического повтора команды нет: пользователь проверяет
черновик и снова сохраняет. Для добавления цены и переименования повторная
команда применяется к свежему документу; история цен сохраняется. Рецепт хранит
в памяти исходную базу вместе с черновиком, в том числе в кэше при уходе в Help.
Трёхстороннее слияние берёт нетронутые поля из свежих данных, изменённые владельцем —
из черновика. Изменённое обеими сторонами поле требует выбора перед сохранением;
неразрешённые расхождения переживают навигацию. Состав (массив lines) сравнивается
как одно поле; количество и единица выхода заготовки проверяются вместе.
Сериализация исходного рецепта/документа мемоизирована по ссылке.

События `storage` и повторная активация обновляют вкладку автоматически, если нет
открытой формы/диалога или несохранённых рецептов/сценариев. Источники черновиков
зарегистрированы независимо; кэши продолжают защищать данные при переходе в Help.
После закрытия формы/удаления черновика проверка повторяется. Открытая форма консервативно
считается черновиком даже до первого ввода: это защищает локальное состояние
существующих редакторов. В таком случае показывается уведомление; сама форма не
перемонтируется. Если свежие данные удаляют именно сущность, связанную с формой/черновиком,
загрузка отклоняется до изменения store: UI предлагает скопировать нужное из
черновика и закрыть форму. Для удалённой цели припаркованного рецепта есть отдельный текст
и удаление именно её кэшированного черновика; остальные черновики сохраняются. Действие загрузки доступно и внутри фокус-ловушки диалога.

Гарантия: сериализация и отсутствие молчаливой перезаписи устаревшим документом
между вкладками **этой версии**, одного origin/профиля, использующими этот
протокол. Одиночная запись `setItem` атомарна в смысле «полный документ или
ошибка»; это не транзакция между устройствами и не обещание сохранности при
очистке браузера. Предыдущий клиент v1 с CAS использует тот же Web Lock; после
записи v2 его устаревшая команда получает конфликт, а перезагрузка показывает
неподдерживаемый формат. Более ранние клиенты без CAS, DevTools и сторонний код
могут писать напрямую: от такого обхода браузерный протокол не защищает.
В тестах память изолирована; отдельно проверяются очередь блокировок и конфликт
двух store.

Если сохранённый документ исчезает (`было → null`), экран сохраняет копию в памяти
и предлагает скачать её либо с подтверждением сохранить как новые данные; демо не подставляется.
Сохранение из памяти допустимо только пока хранилище всё ещё пусто, затем снова
действуют обычные CAS/история. Несохранённые поля формы остаются черновиком.
Load latest остаётся доступным, если другая вкладка уже заполнила хранилище. «Load latest» при повреждении
переходит в восстановление. В симуляторе сравнение использует свежие реальные
данные, а прежние baseline сценариев явно отмечаются как устаревшие до Update baseline.

Повреждённый JSON/неподдерживаемый формат открывают режим восстановления.
Исходный текст доступен для скачивания как UTF-8 через Blob. NUL и обычные Unicode-символы
сохраняются; одиночные суррогаты UTF-16 преобразуются в U+FFFD. Это честно указано
в режиме восстановления: произвольно повреждённая строка не всегда сохраняется побитово. Backup проверяется
общим парсером и валидатором, затем повторно адаптером при подтверждённой записи.
Сброс к демо/пустому документу требует подтверждения с предложением скачать
оригинал; ошибка проверки, конфликт, отказ записи или отмена его не заменяют.


### Сохранность данных: CAS, история версий и файл-копия

CAS защищает от молчаливой перезаписи свежих данных устаревшей вкладкой.
История помогает отменить ошибочную правку. Независимый файл-копия нужен при
очистке браузера, потере профиля или устройства. Ни CAS, ни история в том же
браузере не обещают аварийный RPO «не более пяти минут»; еженедельный Export
при регулярном выполнении допускает до недели потери, а без него — больше.

История — десять отдельных ключей `menupilot:history:0` … `:9`; общего индекса нет.
Каждый содержит UUID снимка, порядковый номер, время архивации и точный предыдущий
сырой текст. Лимиты: до десяти предыдущих версий и до 1 MiB суммарно, учитывая
по два байта на кодовую единицу UTF-16 ключей и сериализованных значений.
Время в списке — момент помещения предыдущего документа в историю, а не время
первой правки. Порядок определяется номером даже при переводе часов назад.

Вся запись и очистка снимков идут под тем же `menupilot:document-writer` Web Lock:
перечитать → проверить текст и маркер CAS → сохранить предыдущий текст →
записать новый маркер → записать основной документ → обновить экран.
Обычное сохранение неизменённого v2 после проверки CAS ничего не пишет;
миграция, импорт, сброс и восстановление создают новую ревизию. Снимок,
совпадающий с новейшим в истории, повторно не добавляется.
При сбое до последнего шага допустим лишний снимок. Новейший снимок текущего
документа не удаляется ради записи основного документа. Одна запись localStorage
атомарна; весь набор ключей не является транзакцией и не даёт гарантий fsync.

При нехватке квоты удаляются старейшие автоматические снимки. Если снимок всё
равно не помещается, обычное редактирование разрешено с заметным предупреждением
«Version history is unavailable» и предложением Export. Исходник миграции v1
защищается отдельно вне этого бюджета (см. ниже). Если не помещается
основной документ или маркер безопасной записи — отказ; прежние данные и черновик
остаются. Импорт, Reset и восстановление требуют сохранить текущий сырой текст
в историю; для мигрируемого v1 эту гарантию заменяет отдельный исходник или
подтверждённое скачивание (см. ниже). В остальных случаях при невозможности
архивации разрушительная замена отменяется. Нужно экспортировать
файл и освободить место. Если текущий документ сам превышает бюджет снимка 1 MiB,
такая замена тоже блокируется; обычное редактирование и Export остаются доступны.

Data и режим восстановления получают список только с метаданными времени.
Выбранная версия читается отдельно при открытии предпросмотра; там показаны
количества блюд, заготовок, ингредиентов и сценариев, а также отличающиеся записи (включая
добавленные/удалённые) и изменение настроек. При выборе повреждённого снимка
появляется понятный отказ; подтверждение восстановления не открывается. Восстановление повторно валидирует снимок и
пишет **новую** ревизию через CAS, архивируя текущую. Оно требует подтверждения
и очищает черновики рецептов/сценариев только после успешной записи. Выбранный
снимок защищён от перезаписи слота и удаления ради квоты до успеха основной
записи; при отказе его можно выбрать повторно. Для цен из будущего выводится
отдельное сообщение с предложением проверить часы или выбрать другую версию.

`menupilot:backup` хранит начало работы со своими данными и дату последнего
запроса Export. Отсчёт начинается при первом успешном изменении, импорте или
переходе к пустым данным; просто открытое демо не запускает напоминание, Reset
к демо останавливает его. Через семь дней после более поздней из дат начала и
Export показывается мягкое напоминание, также в долго открытой вкладке.
«Remind me later» откладывает его на семь дней отдельной датой `remindedAt`,
не меняя дату Export.
Метаданные напоминания — best effort: их отказ не отменяет уже совершённое
сохранение/скачивание. Ошибка записи даты Export или отсрочки явно показана
в интерфейсе, напоминание при ней не сбрасывается. Дата означает запрос скачивания, а не подтверждённое
наличие файла на диске. Очистка браузера удаляет и документ, и историю, и эти даты.

### Слой хранения и ревизии

`src/store/store.js` содержит общие команды каталога, сценариев и настроек.
Доменные проверки находятся в `schema.js`, `entities.js`, `scenario.js`, `graph.js`;
расчёты — только в `src/calc/`. Общие `parseBackup` и `serializeBackup` отвечают
за файлы импорта/экспорта. UI передаёт текст в store, не парсит документ.
На входе проверяются размер, формат, метаданные и каталог; сериализация уже
проверенного документа не запускает повторную валидацию. Сервер D/C повторяет
общую валидацию на своей доверенной границе.

Контракт readonly-типами описан в `src/ui/domain/storageAdapter.ts`:

```ts
load({ beforeReplace? }?) -> Promise<StoredDocument>
save(document, expectedRevision, opId) -> Promise<WriteResult>
importDocument(source: StoredDocument, expectedRevision, opId) -> Promise<WriteResult>
reset(document, expectedRevision, opId, kind: 'empty' | 'demo') -> Promise<WriteResult>
history.list() -> Promise<HistoryEntry[]> // только id, order, savedAt; без raw/document
history.read(id) -> Promise<StoredDocument>
history.restore(id, expectedRevision, opId) -> Promise<WriteResult>
saveMemoryAsNew(document, opId) -> Promise<WriteResult>
subscribe?(changed) -> unsubscribe
// StoredDocument = { document, schemaVersion, documentId, revision }
// WriteResult = StoredDocument | { conflict: true, revision, documentId, document? }
```

Store экспортирует свой опубликованный документ через общую сериализацию; импорт
разбирает и валидирует до вызова `importDocument`. Адаптер получает проверенный
документ, а не текст файла. Конфликт — результат с последней доступной ревизией и
документом для сравнения; store превращает его в `StoreError('conflict')` с `latest`
для существующего UI. Ошибки ввода/хранения отклоняют Promise со стабильным `code`.
`beforeReplace` защищает редактор от удаления его сущности при загрузке: если callback
отклоняет замену, адаптер не продвигает токен CAS. `saveMemoryAsNew` разрешён только
при отсутствии текущего сохранённого документа.

`BrowserStorageAdapter` отвечает за localStorage, Web Locks, CAS и историю.
Его `browserRecovery` отдельно предоставляет сырой текст повреждённого документа,
явное открытие recovery и подтверждение скачанного исходника миграции;
`browserMetadata` отдельно обслуживает предупреждение истории и напоминание Export.
Они не входят в общий StorageAdapter. Флаги браузерной политики архивации также
не передаются через общий интерфейс. DataProvider использует browser-возможности
только когда они присутствуют; серверный адаптер уведомляет его через `subscribe`.
Новая реализация передаётся через `createStore(..., { adapter })` или
`<DataProvider adapter={...}>`; экраны не вызывают транспорт.

Каждая запись получает `opId`, созданный store один раз перед передачей адаптеру.
Транспорт повторяет запрос с тем же `opId`, а не повторяет доменную операцию.
Повтор подтверждённой операции возвращает актуальное сохранённое состояние без
новой записи, в том числе после перезапуска адаптера. В браузере последние 128
ID записываются атомарно вместе с документом в необязательном поле `operationIds`;
экспорт не переносит эти служебные квитанции. Операция с одним ID обозначает один
неизменный запрос: повторно использовать ID для другой команды запрещено.
После выхода ID из окна повтор со старой ревизией получает конфликт. Нулевая
операция (обычное сохранение идентичного документа) не меняет данные/историю.
Для D/C квитанции должны храниться сервером транзакционно с документом и иметь
явную серверную политику срока хранения. Автоматической офлайн-очереди здесь нет.

Команды store и `execute` возвращают Promise. `execute` показывает Saving/Opslaan,
ждёт подтверждения и только затем передаёт чистому reducer `documentReplaced`.
Saved/Opgeslagen сбрасывается через 3 секунды или при смене маршрута. Ошибка команды
имеет нейтральный текст; подробности и конфликт отображаются отдельно. Чтение
при reload/storage-событии не показывает Saving. Пока запись ожидается, поля и
подтверждение заблокированы; после отказа/таймаута форма снова доступна, ввод
сохранён, диалог можно закрыть. Синхронные предохранители store и DataProvider
отсекают двойной клик. Черновики рецептов и симулятора очищаются только после
успешной команды. Завершение создания рецепта не меняет маршрут после ухода
пользователя со страницы. Эффект загрузки не пишет, устаревшие результаты StrictMode
игнорируются; reducer не имеет побочных эффектов.

Формат хранения v2 — оболочка над доменным каталогом:

```json
{
  "version": 2,
  "schemaVersion": 2,
  "documentId": "UUID",
  "revision": 17,
  "document": {
    "version": 1,
    "settings": { "defaultVatRateBp": 900 },
    "ingredients": [], "recipes": [], "scenarios": []
  }
}
```

Версия оболочки (`schemaVersion` и её защитный внешний `version`) и версия домена
(`document.version`) независимы: будущая миграция каталога не меняет автоматически
версию оболочки, и наоборот. Внешний `version: 2` нужен старому клиенту: тот видит
понятный отказ «новый формат». Ключ остаётся `menupilot:v1`, иначе старый клиент
увидел бы пустое хранилище. Демо EN/NL остаются доменными v1.

`documentId` назначает адаптер; в D/C — сам сервер, а не UI/импортируемый файл.
Обычная правка и возврат версии сохраняют ID. Reset to empty/demo, начало заново
и сохранение памяти как нового набора выпускают новый ID. Если ID импортируемого
файла отличается от текущего (или отсутствует в v1), адаптер всегда выпускает
свой новый ID, без вопроса пользователю. Импорт своей копии сохраняет ID.
До первой записи ID равен null, и экспорт выдаёт обычный v1-каталог без случайной
неподтверждённой идентичности. UUID создаётся лениво; при отсутствии randomUUID
используется getRandomValues, доступный в HTTP LAN-контексте.

Адаптер запоминает идентичность последней успешной загрузки. Транспорт D/C
передаёт её вместе с expectedRevision: CAS проверяет пару documentId/revision,
чтобы одинаковые номера разных наборов не считались одной версией.

`revision` — безопасное неотрицательное целое, монотонное **в пределах documentId**.
Импорт/возврат версии не присваивают сохранённый в файле номер: создают новую
ревизию, даже при одинаковом содержимом. Браузер дополнительно продолжает единый
счётчик между наборами; серверу это не требуется. Переполнение отклоняется.
Отказ записи может оставить пропуск; зарезервированный номер не используется снова.

Миграция v1 → v2 происходит при первой явной записи, загрузка ничего не меняет.
Перед миграцией **точный исходный текст v1** сохраняется в отдельном ключе
`menupilot:premigration-v1`, вне бюджета истории 1 MiB и вне её удаления при квоте.
Этот ключ не очищается обычными записями. Если в будущем снова мигрирует другой
v1-исходник, ключ заменяется им только перед такой миграцией; обычная история
остаётся дополнительной копией. Если отдельную копию сохранить невозможно,
возвращается `migration-backup-required`, текущие данные и черновики остаются.
UI предлагает скачать точный исходник, проверить скачанный файл и явно подтвердить.
Подтверждение связано с конкретным исходным текстом и проверяется перед повтором;
оно не является записью, после него пользователь повторяет свою команду.
Без сохранённой копии или такого подтверждения миграция не разрешается.
Исходник >600 тысяч символов проверен на 200 ингредиентах × 28 цен.
Файлы v1 импортируются через общий parser, исторические v1-снимки читаются.

CAS под Web Lock сравнивает ожидаемую ревизию, точный исходный текст и
`menupilot:revision`. Текст защищает от старого клиента/внешней записи без новой
метадаты, маркер — от прерванной записи/ABA. После резервной копии/истории адаптер
пишет high-water mark, затем атомарно весь основной JSON. Новый номер больше
опубликованного и зарезервированного. История и основной документ не являются
общей транзакцией. Browser storage не гарантирует fsync или независимую копию.
Удаление всех браузерных данных удаляет и счётчик, и историю, и premigration.

Web Lock берётся на одну операцию. Ожидание ограничено 5 секундами через
AbortController; таймаут даёт `write-busy`, не запускает запись и не прерывает
уже начавшуюся критическую секцию. Без Web Locks запись запрещена. Только явный
`isolated: true` у тестового хранилища/в опциях допускает отсутствие блокировки;
обёртка над localStorage сама по себе ничего не отключает.

D подключается через единственный локальный сервер: сервер назначает documentId,
проверяет документ, выполняет CAS/историю/квитанцию opId в транзакции SQLite.
CLI обращается к нему же. C подключается онлайн через серверный CAS Supabase,
с общей валидацией и правами доступа; клиентское «прочитать, потом записать»
не заменяет атомарный серверный CAS. Серверы, auth и офлайн-очереди не входят в 2a.

`storageAdapterContract(name, fixture)` — отдельные тесты node:test без DOM:
CAS и последняя версия при конфликте, неверная ревизия, метаданные/чтение истории,
неизвестный history ID, восстановление с новой ревизией, чужой импорт с новым ID,
невалидный импорт через общий store, повтор opId после открытия нового адаптера,
отказ записи/повтор. Будущие реализации подставляют свою изолированную фабрику.
Дополнительно проверяются миграция, большой исходник и скачивание, полностью
замороженный клиент v1 (включая зависимости), Web Locks, кэши черновиков и маршруты.

### Локальный режим D1

Сервер находится в `server/`, общий JS-код транспорта и проверки переходов — в
`src/store/`. `npm start` проверяет Node (24.15.0+ в ветке 24 либо 25.8.1+ в ветке
25), канонизирует папку данных, захватывает lock **до открытия основной SQLite БД**, собирает
устаревший/отсутствующий dist и слушает только `127.0.0.1`. Проверенный Node 24.15.0
поставляется с SQLite 3.51.3; также проверен Node 25.8.1 (SQLite 3.52.0).
Сборка использует тот же executable Node; отпечаток учитывает src/data/public,
HTML, конфигурацию Vite, package/lockfile и версию Node. Корень перенаправляет на
`/menupilot/`. При первой загрузке локальная база пуста; демо включается явно.

Папка: macOS `~/Library/Application Support/MenuPilot`, Linux
`$XDG_DATA_HOME/menupilot` или `~/.local/share/menupilot`; `MENUPILOT_DATA_DIR`
переопределяет путь, `realpath` устраняет псевдонимы symlink. `MENUPILOT_PORT` —
1–65535, по умолчанию 4710. SIGINT/SIGTERM закрывают HTTP, делают SQLite checkpoint,
закрывают соединение, затем освобождают собственный lock. Незавершённые HTTP-соединения принудительно закрываются через 1 секунду ожидания; синхронная транзакция SQLite при этом не прерывается. Ошибка запуска тоже
освобождает ресурсы. Токен CLI атомарно заменяется файлом 0600 при запуске; UI
получает другой токен, существующий только в памяти сервера и HTML.

**Протокол единственного писателя.** Все захваты, освобождения и удаления
протухшего lock сериализуются `BEGIN IMMEDIATE` отдельной служебной БД
`lock-coordinator.sqlite` (busy_timeout=5000). Это блокировка ОС, снимаемая при
смерти процесса; файл координатора никогда не удаляется. Она защищает короткую
синхронную секцию `lock.guard`, включая восстановление guard двумя стартёрами.
В этой секции нет сборки, основной БД или HTTP. Основной `menupilot.db` открывается
только победителем после получения lock. `lock` создаётся через `wx` + fsync,
содержит PID, время старта процесса, boot-id, случайный instanceId и адрес.
Linux читает /proc, macOS — ps lstart и kern.bootsessionuuid. Совпавший PID с
другим временем старта/boot-id считается старым; ESRCH также позволяет восстановление.
Неопределённость/EPERM не позволяют вытеснить владельца. Перед «already running»
сервер проверяет GET /menupilot-instance: service=MenuPilot и тот же instanceId.
Этот диагностический маршрут не относится к API и не содержит данных/токенов.
Если процесс жив, но ответа нет, запуск ждёт до 10 секунд, затем сообщает
«lock looks stale or MenuPilot is still starting» и сохраняет lock.
Пустой/невалидный lock старше 5 секунд восстанавливается под guard. Старый guard
(30 секунд) восстанавливается под SQLite-координатором, если в нём нет живого
владельца; неизвестные файлы внутри guard не удаляются. Освобождение сверяет PID
и instanceId, повторяет неудачную очистку трижды и не выбрасывает ошибку наружу.
Все сообщения содержат папку данных, путь lock/guard и одну инструкцию.

**SQLite.** D1/D2: `PRAGMA user_version=1`; D3: `user_version=2` версионирует структуру БД отдельно от оболочки
v2 и домена v1. Более новая версия отвергается. WAL, synchronous=FULL,
busy_timeout=5000, wal_autocheckpoint=1000; при закрытии TRUNCATE checkpoint.
Таблицы: meta, document (одна JSON-запись), history, ops, journal и пустая plans.
`meta.backupDirty` и `backupDirtySince` отмечают изменения для D3 (см. ниже). Политика хранения: history — 32 снимка/64 MiB; ops — 4096 квитанций/4 MiB;
journal — 10000 записей/4 MiB. Удаляются старейшие записи в той же транзакции.
Лимиты байтов относятся к полезным UTF-8 данным, а не накладным страницам SQLite.
Для plans нет API записи, поэтому пока её бюджет равен нулю записей; D5 задаст
сроки и квоты до включения записи. Ошибки SQLite откатывают транзакцию и дают
`write-failed`; испытания реального ENOSPC и потери питания относятся к D3.

**Запись.** HTTP передаёт `{kind, expectedDocumentId, expectedRevision, opId, ...}`.
Клиент не может назначать новую идентичность. Под `BEGIN IMMEDIATE`:

1. Читается текущая пара documentId/revision и вычисляется результат CAS.
2. Проверяется opId. Для уже выполненной **той же логической команды** возвращаются
   исходная квитанция и актуальный документ без записи; другое содержимое даёт
   `op-id-reused`. Эта проверка предшествует отказу по CAS, иначе потерянный ответ
   нельзя было бы повторить после commit. Неизвестный opId + несовпавшая пара дают
   conflict с актуальными documentId/revision/document.
3. Проверяются вид операции, разрешённые поля, метаданные импорта, схема,
   максимальный размер и даты; для save дополнительно вызывается общий
   `assertValidTransition`: прежние цены — неизменный префикс, единица ингредиента
   с ценами/ссылками неизменна, используемый prep нельзя удалить/сменить единицу
   или kind. При удалении блюда его сохранённые сценарии должны быть удалены вместе с ним. Удаление используемой сущности даже одновременно с её ссылками
   требует двух сохранений. Граф, циклы, глубина, неизвестные ссылки проверяются
   общим валидатором. Import/reset/restore/memory — явные отдельные операции.
4. Архивируется прежняя версия, сохраняется следующая, ревизия увеличивается на 1,
   пишется журнал с источником ui/cli и квитанция, применяются бюджеты, затем COMMIT.
   Любой отказ откатывает всё. Save идентичного уже сохранённого документа получает
   квитанцию `changed:false` без увеличения ревизии, истории или журнала.

Квитанция: `{opId, documentId, revision, changed}` — первоначальный результат.
`WriteResult` содержит **актуальный** StoredDocument и необязательное `receipt`;
store публикует актуальный документ, а не исторический результат. Браузерный
адаптер сохраняет прежнее поведение без поля receipt. Хеш SHA-256 использует
канонический JSON логической команды (kind, payload, expectedRevision, opId,
source). Наблюдаемый `expectedDocumentId` — транспортное предусловие, не payload
команды: после повторного открытия адаптер уже видит ID, созданный той же
операцией. Он исключён из хеша, но **всегда проверяется для новой операции**.
Повтор одинаковой команды может только вернуть квитанцию, никогда изменить
другой набор. После выхода квитанции из бюджета повтор со старой парой получает
conflict. Для строгого повтора HTTP сохраняет весь первоначальный JSON запроса.

Номер ревизии в D1 продолжает возрастать и при смене documentId. Импорт чужого
набора/браузерного v1, reset и memory создают новый UUID. Импорт своей копии и
восстановление истории сохраняют ID, но создают новую ревизию. Ни номер, ни ID
импортируемого файла не присваиваются сервером как новая идентичность.

**HTTP и UI.** Разрешены GET document/version/history, POST history/read/write
под `/api/`. Все требуют токен, Host — точный `127.0.0.1:port`. CLI-токен читает,
но raw write требует UI-токен (будущая запись CLI только через D5). Ответы API и
HTML — no-store. D2: одноразовый секрет `#k=…` действует 15 минут. Внешний
login.js заменяет текущую запись session history через replaceState до JSON POST
`/menupilot/session`; гарантии удаления из browser history или sync нет. Секрет
после D5 находится только в памяти сервера и выводе npm start; файла launch-secret
нет. Успешный обмен меняет секрет.

Обмен выдаёт уникальный токен на сеанс в JSON. login.js хранит токен только в
sessionStorage (origin включает порт). Local-config.json и весь API требуют
Authorization: Bearer; конфиг больше не возвращает токен. Cookie HttpOnly,
SameSite=Strict, Path=/menupilot/, Max-Age=36000 открывает только HTML без секретов.
Перехваченная другим loopback-портом cookie не выдаёт конфиг/токен/доступ к API.
Сеанс: абсолютный срок 10 ч, простой 1 ч от последнего авторизованного запроса;
открытый UI опрашивает сервер, но абсолютный срок не продлевается. Максимум 128
сеансов, затем вытесняется старейший. Закрытие вкладки обычно очищает sessionStorage,
но восстановление сеанса браузера может вернуть его. Рестарт отзывает все сеансы.

`npm run menupilot -- open-url` с CLI token через POST `/api/open-url` выпускает
новый секрет, инвалидируя прежний, и сервер сам открывает браузер через execFile
без shell. CLI получает только `{opened: true|false}`, без URL/ключа.
`--revoke-sessions` дополнительно отзывает все сеансы. Чтение файла cookie или открытие новой вкладки не заменяет обмен секрета.
CLI token остаётся отдельным файлом 0600; raw write через него запрещён.

Host строго 127.0.0.1:port; localhost на URL страницы получает HTML-инструкцию
использовать 127.0.0.1, без данных. Foreign/null Origin отклоняются. POST требует
Origin сервера; исключение — CLI token без Origin. GET API требует token и может
не иметь Origin. Маршруты и методы явно перечислены. Dist читается в память до
listen, без symlink/source maps; пересборка не меняет снимок работающего сервера.
Promise каждого request handler перехватывается, обработчик ошибки проверяет
headersSent до заголовков; ошибка формирования error-response тоже изолирована.

CSP: default-src none, script-src self, style-src self unsafe-inline, img-src self
data:, font-src self, connect-src self, base-uri/form-action/frame-ancestors none.
Inline bootstrap темы/языка вынесен сервером в отдельный same-origin JS. Также
CORP/COOP same-origin, X-Frame-Options DENY, nosniff/no-referrer; HTML/API/config
no-store. Тесты проверяют CSP целиком, включая редиректы и bootstrap/login JS.

JSON body ≤15 100 000 UTF-8 байтов (5 млн UTF-16 units плюс metadata), login/open-url
≤1024. Заголовки 10 с, тело 15 с, keep-alive 5 с (Node может добавить 1 с буфера),
максимум 32 соединения и 100 запросов/соединение. Local DoS всё ещё возможен: иной
процесс может постоянно занимать все соединения; гарантии доступности нет.

Диагностика: фиксированные события, время, уровень, HTTP status и короткая причина
host/origin/sign-in/token/size, без свободного текста, URL, токенов, cookie или
документа. Три файла по 1 MiB, MENUPILOT_LOG_LEVEL off/error/warn/info, default warn.
SQLite journal отдельно фиксирует ID, имя и число цен удалённых ингредиентов,
предшествующий документ сохраняется в history той же транзакцией.

Граница: утечка UI token даёт полный доступ чтения/записи до отзыва/истечения,
поскольку native client может подставить Origin. Cookie сама по себе API-доступа
не даёт. Процессы того же OS user читают 0600/БД; root, расширения и скомпрометированный
браузер не изолированы. Секрет может остаться в browser history или sync; использованный,
заменённый и просроченный секрет недействителен. Это не доказательство согласия человека.

`HttpStorageAdapter` реализует тот же контракт, `beforeReplace` вызывается до
продвижения CAS, история-предпросмотр не двигает CAS. Не более трёх сетевых попыток
(таймаут 8 с каждая, задержки 150/300 мс) с тем же JSON/opId. При неоднозначном
обрыве UI сообщает, что запись могла пройти, и предлагает сначала загрузить
актуальные данные. Очереди записи офлайн нет. Подписка опрашивает маленькую пару
ID/revision раз в 2 с без перекрывающихся запросов: для одного локального сервера
это проще SSE, сохраняет существующую защиту открытых черновиков, не удерживает
соединение при остановке. Подписка очищает таймер при размонтировании.

После перезапуска меняется токен: старый UI получает 401, показывает инструкцию
сначала скопировать черновики и обновить страницу; сам не перезагружается и не
переключается на браузерную БД. Ошибка конфига также блокирует запуск, без fallback.
В шапке EN/NL показываются локальный режим и канонический путь. Импорт локально
валидируется до диалога, показывает количества блюд/prep/ингредиентов/сценариев и
предупреждение о замене без объединения. Исходный файл и браузерная БД не меняются.

Уточнения ревью D1: reset проверяет точное совпадение с emptyDocument() или
встроенным EN/NL demo с одинаковым сдвигом всех дат; произвольные данные доступны
только через явный import. Content-Length проверяется до чтения, потоковое тело
тоже ограничено, 413 закрывает соединение. Неверное тело history/read даёт 400.
`npm test` (и `check`) включает серверные тесты и мутации; CI закреплён на 24.15.0.


### Локальные копии и восстановление D3

`server/backups.js` оборачивает синхронный SQLite-адаптер общей Promise-очередью.
Все производственные записи, снимки и восстановления идут через неё; внешний
process lock по-прежнему захватывается до открытия основной базы. `backup()`
асинхронен, поэтому держать только SQLite-транзакцию недостаточно: очередь не
пускает другую запись между снимком непосредственно перед заменой и COMMIT.
Чтения доступны во время копирования. HTTP ждёт Promise записи до ответа.

`backupDirty=1` и время **первого** ещё не скопированного изменения пишутся в той
же транзакции, что document/history/ops/journal. Повтор opId, CAS-конфликт и
неизменившийся save не пачкают документ. Таймер проверяет раз в секунду, запускает
снимок через 4 минуты (минута запаса до цели ≤5 минут); повторный save не сдвигает
срок. Внутри сеанса используется monotonic clock плюс сохранённое время; откат
wall clock не задерживает копирование. Каждый tick сравнивает wall delta и monotonic
delta (расхождение >60 с или любой откат wall clock). Скачок в обе стороны сохраняет
`backupClockWarning=1`: удаление в обоих каталогах приостановлено, включая перезапуск.
Пауза автоматически не снимается; квоты остаются, старые файлы архивируются вручную.
Ежедневный дедлайн хранится в monotonic time, сбрасывается после успешного снимка;
при скачке ближайший снимок становится due. Будущие метаданные не блокируют расписание. При запуске dirty копируется сразу,
при остановке HTTP закрывается, очередь дожидается операций, dirty копируется,
затем checkpoint/close и release lock. Неудачная автоматическая копия сохраняет
флаг, показывает ошибку и повторяется. Неподвижный документ получает ежедневный
снимок при работающем сервере. Сон/остановка/зависший диск не дают жёсткой гарантии
пяти минут; просрочка видима, а время последнего успеха — фактический предел RPO.

`server/backupFiles.js`: SQLite `backup()` → уникальный `.sqlite.partial` →
DELETE journal mode на копии → встроенные metadata (`id`, `documentId`, `revision`,
`createdAt`, `dbVersion`, `reason`, монотонная `sequence`) → `integrity_check` и
общая валидация документа/истории → fsync файла → rename `.sqlite` → fsync каталога.
Только после публикации в транзакции очищаются dirty/dirtySince. Сбой до очистки
даёт лишнюю копию после перезапуска, а не потерю. Неготовые файлы не перечисляются;
остатки известных partial-файлов убираются после получения process lock. Схема
копии версионируется `user_version`, независимо от JSON domain v1 / envelope v2.

D3 обновляет структуру 1→2 только после проверенной копии `before-migration`, под
process lock, до транзакции миграции. При ошибке копии версия остаётся 1. Старый
сервер D1/D2 отказывается открывать v2. Для восстановления v1-копии документ
читается общим валидатором; обычный restore не переносит её структуру в живую БД.

Политика: все снимки за сутки + последний по порядку создания на каждый из 14
предыдущих представленных UTC-дней плюс минимум два последних проверенных снимка
(новый и запасной, если доступны). Отсутствующие дни не выдумываются. До удаления
кандидаты проходят настоящий restore-test. Замена публикуется до ротации; ошибка
публикации не удаляет старые исправные точки. Повреждённые файлы атомарно переносятся
в `quarantine/`, исключаются из точек восстановления и видимы в статусе. Ошибка
исполнения проверки (например, недоступный временный диск) отменяет удаление. Порядок
определяется `sequence`, чтобы откат часов не менял «последний снимок». Будущие
относительно текущих часов метки не удаляются автоматически. Лимит 512 файлов /
2 GiB ограничивает рост; при несовместимости лимита с окном хранения новый снимок
отклоняется с видимой ошибкой, свежие точки молча не выбрасываются. Невалидные
готовые файлы, включая quarantine, считаются в бюджете и требуют ручного разбора. Существующие бюджеты
history/ops/journal остаются; SQLite переиспользует свободные страницы (не обещаем
равенства размера файла и JSON-бюджета). Аварийные архивы не удаляются автоматически.

Перед import/reset/restore/memory/backup-restore — проверенная копия текущей пары
ID/revision. Дубликат квитанции или CAS-конфликт не требует лишней копии. Ошибка
копии блокирует замену. `backup-restore` — внутренний вид команды, недоступный через
raw `/api/write`: CLI endpoint получает ID, expectedDocumentId/expectedRevision,
opId; сервер restore-тестирует копию, затем пишет её документ через тот же
валидатор, CAS, историю, journal и receipt. Текущий ID сохраняется, revision +1.
Повтор квитанции работает и после выхода исходной копии из retention.

`MENUPILOT_BACKUP_DIR`: существующая внешняя папка и отдельный installation UUID
подкаталог. Публикуются только проверенные готовые локальные файлы, сначала новая
копия, потом backlog. На приёмнике temporary → проверка → fsync/rename/fsync.
Время успешной внешней записи хранится в meta вместе с путём и snapshot metadata;
смена назначения не использует успех прежней папки. Повтор — exponential backoff
1 с…5 мин. Проверка существующих внешних копий в простое — не чаще раза в минуту;
новый снимок экспортируется сразу. Для внешней папки тоже действуют retention и бюджет. Запись в облачную
папку **не доказывает** синхронизацию. Startup предупреждает по известным облачным
путям/типам сетевых файловых систем; это эвристика. Живая база — только локально.

Авторизованные GET `/api/backups` и `/api/backups/status`; POST
`/api/backups/verify` (только ID) и `/api/backups/restore` (CLI token, CAS/opId).
Сохраняются Host/Origin/token правила D2; UI token не вызывает CLI restore. Verify
восстанавливает копию SQLite Backup API в временную БД, проверяет целостность,
документ, историю и связь metadata, затем удаляет только свою временную БД.
`doctor` без флагов выводит авторизованный статус, предупреждения о часах и quarantine.
CLI спрашивает RESTORE; `--yes` разрешён скриптам. Сервер должен работать.
Индикатор EN/NL в локальной шапке опрашивает статус раз в 5 с: времена копий,
dirty, ошибки, задержка >5 мин, отсутствие внешнего успеха за сутки, повреждённые
копии и приостановка удаления после скачка часов. Его состояние
не входит в документ/редьюсеры; не меняет формы. Расширение UI только наблюдательное.

`doctor --recover-from-backup <id>` — отдельный **offline** протокол, с тем же lock.
До касания оригиналов проверяет восстановление. Создаёт durable intent
`recovery-pending.json`, сохраняет основной файл и WAL/SHM рядом в уникальном
`recovery-UUID/`, устанавливает проверенную временную БД и пишет отчёт. При падении
нормальный запуск блокируется по intent; повтор той же команды сохраняет также
остатки прежней попытки. Оригиналы не открываются/checkpoint-ятся и не затираются.
Новый dataset ID исключает случайное совпадение CAS со старым клиентом; счётчик
берётся из snapshot +1, прежний недоступный high-water неизвестен. Ops/plans
инвалидируются, journal получает emergency-recovery, dirty=1. Это физическое
аварийное восстановление с потерей изменений после копии, не обычный restore.

Испытания: SIGKILL именно внутри реального SQLite backup шага; SQLite FULL через
max_page_count; ENOSPC на границе копирования; сериализация import/pre-copy и CAS;
новая ревизия/журнал/receipt restore; верификация всех созданных в сценарии копий;
недоступное внешнее назначение/backoff; startup/shutdown; часы ±сутки/неделя и возврат; retention и повреждённый keeper в обоих каталогах;
миграция и отказ её копии; аварийный архив/intent; мутации ключевых защит.
SIGKILL и эмуляция FULL не заменяют испытания физического отключения питания.

### D5 — supplier-price plans and owner confirmation

The existing DB v2 `plans(id, expiresAt, plan)` table stores protocol-v1 JSON; no SQL structure or document schema change is made, so no migration is required. Document `schemaVersion` stays unchanged. `server/plans.js` owns normalized proposals, lifecycle, budgets and the approval transaction; `server/planEffects.js` composes existing `src/calc` functions without new formulas. Plans fix document ID/revision, exact ingredient ID, price sequence/timestamp and operation ID before showing consequences. Exact lookup accepts NFC/case-normalized IDs/names; ambiguity never selects a candidate.

`src/store/price.js` extracts the former store `newPrice` construction and ingredient lookup/append into shared helpers. Manual add-price and plan application both call this path; full document validation and append-only transition checks remain on persistence. Existing clock-backwards behavior and zero-price acceptance are preserved. Plans store cents as decimal strings on the wire; applying reconstructs the previously validated safe integer. New domain IDs are not invented for prices (the existing price identity is `seq`).

Apply runs in one SQLite `BEGIN IMMEDIATE`: check current documentId/revision and expiry; append the fixed price with shared validation; execute the existing write path under the same transaction; save revision/history/journal (`source: agent`, `confirmedBy: ui`), receipt and applied plan; COMMIT. A failure even at the final plans UPDATE rolls everything back. The internal `withinTransaction` option is server-only and cannot be passed through HTTP. Reapplying an applied plan returns its original receipt and the current document, before stale checks, including after a restart. Plan mutations mark the database dirty for D3 backups. All plan access (including lazy lifecycle cleanup) shares D3's writer/backup queue, preventing mutations between a pre-replacement snapshot and its replacement.

Statuses: pending → applied/rejected/superseded, or stale when document identity/revision differs, or expired at the 24-hour boundary. Refresh persists stale/expired before returning the refusal. Terminal plans are kept until seven days after expiry, subject to 200 total/2 MiB retention; pending count is limited to 50 and each proposed JSON to 256 KiB. Terminal plans may be evicted oldest first; pending plans for other ingredients cannot be evicted to accommodate another proposal. Plan endpoint replay is bounded by this retention. The independently bounded `ops` table retains its existing contract.

Consequences use Dashboard results for before/after catalogs, `costChangeCents`, `foodCostChangeTenths`, `monthlyContributionCents`, `monthlyImpactCents` and `menuMonthlyImpactCents`. Dependency traversal includes all parent prep levels. Comparison is the actual pre-proposal catalog (not a timestamp approximation, which could select a same-millisecond price incorrectly). Unknown is null; no-volume dishes are excluded, and excluded unknown counts accompany the known-only total. No calculations are duplicated in UI.

`httpPlanAdapter.ts` provides typed, authenticated plan reads/actions and `subscribe` polling, including initial loading and error recovery. `LocalPlans` exists only in local mode; EN/NL confirmation dialogs use the existing Radix focus/keyboard primitives. Document revision polling continues through the existing HTTP StorageAdapter → store.load/beforeReplace → documentReplaced flow. Plan notifications do not create false document conflicts; after approval existing draft protection defers document replacement when a form/dialog is open. A lost action response is reported; reapproval is safe and queue polling recovers the status.

Apply/reject require the session registry's UI bearer identity plus the exact Origin; supplying CLI bearer with the correct Origin is still forbidden (403 `ui-required`). No body field can claim UI authority. Read/propose are available to CLI. This is protection against errors and hostile websites, not isolation from a local process with full user privileges.

D5 review hardening: launch capabilities are held in server memory and printed by startup; the browser launcher also briefly receives the key as a process argument, which a same-user process could intercept. The CLI `open-url` endpoint invokes the OS browser launcher via execFile and returns only `{opened}`. No launch-secret file remains. This enforces UI confirmation in normal operation; shell access is not isolated from direct database/process access.

A valid new proposal atomically supersedes a pending proposal for the same ingredient (`supersedes` / `supersededBy`). Invalid proposals preserve the old one. Agent pack prices are capped at €100,000; zero prices and exact unit-price ratios exceeding ×3 in either direction produce warnings. These guardrails do not change manual price validation or costing formulas. Price ratio warnings compare integer cross-products without rounding. Stale/expired apply/reject returns HTTP 409. Journal entries include planId and ingredientId. Plan listing returns the document version and plans in one writer-queue snapshot; CLI presentation converts money to the D4 `{cents|micro,display}` contract.

The local panel shows at most one pending card below 640 px, or three on desktop, with paging and a confirmed Reject all action. Stale/expired/rejected/superseded entries occupy one dismissible summary line; one status region announces queue changes. Warning text appears in both card and confirmation dialog. Success messages clear on the next action or after five seconds.
