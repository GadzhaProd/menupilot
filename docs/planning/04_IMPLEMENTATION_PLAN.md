# 04. План реализации MenuPilot (MVP)

**Статус:** этапы 0–7 выполнены (каркас, расчёты, симуляция, хранилище, UI ингредиентов и рецептов, Dashboard, Profit Simulator, резервные копии, полировка и README). Демо: https://gadzhaprod.github.io/menupilot/

Основа — архитектура из `03_ARCHITECTURE.md`. Каждый этап завершается коммитом, отчётом владельцу по 6 пунктам (см. `05_AGENT_RULES_DRAFT.md`) и прогоном `npm run check`. Код каждого этапа проверяет независимый ревьюер другого вендора.

Сложность: **S** — до 2 ч, **M** — 2–4 ч, **L** — 4–8 ч.

| # | Этап | Зависит от | Сложность |
|---|---|---|---|
| 0 | Каркас проекта и правила агентов | — | S |
| 1 | Модуль расчётов, включая заготовки (TDD) | 0 | M–L |
| 2 | Симуляция и сравнение (TDD) | 1 | M |
| 3 | Хранилище, валидация, демо-данные | 1 | M–L |
| 4a | React-каркас, типизированная граница, тесты, CI/Pages | 1, 3 | M–L |
| 4b | UI ингредиентов, рецептов и заготовок | 4a | L |
| 5 | Dashboard с изменениями и месячным эффектом | 4b | M–L |
| 6 | Profit Simulator и сравнение сценариев | 2, 4b | L |
| 7 | Полировка, README, скриншоты, демо | 5, 6 | M |

Этапы 2 и 3 независимы и могут идти параллельно.

### Этап 0. Каркас
**Цель:** пустой, но запускаемый проект.
**Задачи:**
- Vite + React 19 + TypeScript strict + Tailwind v4, точные версии разрешённых зависимостей и lockfile;
- `npm run typecheck`, `test:core`, `test:ui`, `test`, `build`, `check`;
- пустая страница `index.html`;
- `AGENTS.md` и `CLAUDE.md` (по черновику 05);
- `.gitignore`;
- `README.md`-заготовка.

**Тесты:** `test:core` запускает только `node:test` по явным путям/глобам `test/calc` и `test/store`; `test:ui` запускает только `vitest run` для UI в jsdom. `npm test` запускает оба и возвращает ошибку при падении любого. Каталог `node --test test/` не использовать (на Node 25 он падает).
**Приёмка:** `npm run dev` открывает React-каркас; `npm run typecheck`, `npm test` и `npm run build` проходят. CI настроен для GitHub Pages, production base `/menupilot/`, hash-маршруты `#/`, `#/ingredients`, `#/recipe/:id`, `#/simulator/:id`. Production-сборка проверена через `vite preview` с base в подпапке.

### Этап 1. Модуль расчётов
**Цель:** все формулы из раздела 6 архитектуры, без интерфейса.
**Задачи:**
- `money.js`: разбор `"12,50"`, `"12.5"`, `"€12"`, отказ для `"abc"`, `"-1"` и лишних знаков; `roundDiv`; форматирование EUR;
- `units.js`: совместимость единиц и отображаемая цена kg/l/pc без изменения хранения;
- `costing.js`: строки ингредиентов и рекурсивные строки заготовок, `batchCostµ`, неизвестная стоимость.

**Тесты (пишутся первыми):**
- контрольный пример из ТЗ;
- ручной пересчёт 3 блюд;
- выход 80% и 100%;
- несколько порций;
- граница half away from zero, в том числе для отрицательных значений;
- НДС 9% и 21%;
- нулевая цена продажи → «n/a»;
- отсутствующая цена → unknown;
- нулевое количество отклоняется;
- большие значения без переполнения;
- несовместимые единицы отклоняются.
- эквивалентная цена упаковки: €11,20 за 1 kg → €11.20/kg; €2,80 за 250 g → €11.20/kg (показ, хранение не меняется);
- заготовки в 2–3 уровня, точный ручной пример из 03 (€1,80/kg соуса; 150 g = €0,27), округление на строке;
- неизвестная стоимость проходит через заготовку; несовпадение единиц отклоняется.

**Приёмка:** все тесты проходят; в `calc/` нет `parseFloat` и нет операций с float над деньгами.

### Этап 2. Симуляция
**Цель:** `simulate(snapshot, overrides)` и `compare`.
**Тесты:**
- сценарии A/B/C из ТЗ;
- изменение цены ингредиента, граммовки, цены в меню и объёма;
- объём 0;
- отрицательный contribution;
- входные данные не изменились (deep-freeze и сравнение до и после);
- разница считается от отображаемых значений.
- override цены ингредиента пересчитывает блюдо через 2–3 уровня prep; override количества меняет только строки блюда; тест против ошибки масштаба: 150 g из партии 1 kg стоит 15% стоимости партии, а не стоимость полной партии/порции prep.
- baseline snapshot содержит все используемые заготовки и цены; unknown проходит наверх.

**Приёмка:** пример из ТЗ даёт −€0,65 и −€195,00; тест изоляции проходит.

### Этап 3. Хранилище
**Цель:** надёжное сохранение и загрузка.
**Задачи:**
- `schema.js`: проверка документа и версии;
- проверка `kind`, полей dish/prep, ссылок `ref`, безопасных `outputMilli`, единиц, циклов и максимальной глубины 5; запрет удаления используемой сущности;
- `store.js`: загрузка, сохранение, добавление цены в историю, экспорт и импорт, сброс к демо;
- `data/demo.json`: 8–10 ингредиентов и 5–6 блюд нидерландского кафе с ценами в EUR, история цен за 2 месяца.

**Тесты:**
- сохранение и загрузка «после перезапуска» на хранилище в памяти;
- битый JSON и неверная версия → понятная ошибка, данные не тронуты;
- ошибка записи (переполнение) → сообщение;
- импорт не портит текущие данные при ошибке;
- история цен только дописывается;
- цена на дату выбирается по `recordedAt` и `seq`.
- импорт/сохранение отклоняют самоссылку и цикл A→B→A; цена истории и размеры упаковок сохраняются.

**Приёмка:** тесты проходят; демо-данные загружаются при первом запуске.

### Этап 4a. React-каркас и граница типов
**Цель:** подключить новый UI, не меняя поведение JS-ядра.
**Задачи:**
- Vite, React 19, TypeScript strict, Tailwind v4, shadcn/ui, алиас `@` → `src`; экраны в `src/ui/`, компоненты shadcn в `src/components/ui/`;
- тонкий `src/ui/domain/*.ts`: readonly-типы документа (ingredient, price, dish | prep recipe, line, scenario, baseline, overrides), результатов расчётов с `BigInt` и методов store;
- чистый reducer и контракт `store` → успешный `documentReplaced`; ошибка сохраняет прежний документ; формы локальны, результаты calc производны и не сериализуются;
- раздельные core/UI test-команды, typecheck и GitHub Actions: typecheck, test, build, deploy Pages на push в main;
- hash-роутер, импорт `demo.json` через Vite; production base `/menupilot/`.

**Тесты и проверка:** `test:core` — только `node:test` для calc/store с явными путями/глобами; `test:ui` — только `vitest run` для UI (jsdom + Testing Library); `npm test` выполняет оба. Проверить production build через `vite preview` в подпапке `/menupilot/`. Реальный браузер через bb browser-automation: скриншоты desktop и 375 px, клавиатура/фокус диалогов и ошибки полей.
**Приёмка:** `npm run check` проходит локально и в CI; приложение открывает все четыре маршрута на GitHub Pages, production-ресурсы загружаются из `/menupilot/`, а типизированная граница не переписывает ядро.

### Этап 4b. UI: ингредиенты, рецепты и заготовки
**Цель:** владелец может заводить свои данные.
**Задачи:**
- навигация и экраны Ingredients и Recipe;
- экран Ingredients: список, добавление, новая цена, история;
- у цены упаковки — отображение за kg/l/pc и подсказка “Supplier price excl. VAT, as on the invoice”;
- экран Recipe: dish/prep, состав из ингредиентов и заготовок, количества/выходы, цена блюда с НДС и ставкой, выход партии prep, себестоимость блюда на порцию и заготовки на партию;
- ошибки ввода показываются рядом с полем.

**Тесты и проверка:** тесты логики и reducer в Vitest; несовместимая единица и ссылка на удаляемую сущность отклоняются. Каждый UI-этап проверяется в реальном браузере через bb browser-automation: desktop и 375 px, клавиатура/фокус диалогов, ошибки полей.
**Приёмка:** сценарий 3 спецификации выполнен, данные переживают перезагрузку страницы, мобильная ширина читается, ошибки видны рядом с полями.

### Этап 5. Dashboard
**Цель:** ответ на вопрос «что подорожало».
**Задачи:**
- таблица блюд: цена без НДС, себестоимость, contribution, food cost %, изменение себестоимости относительно даты сравнения (по умолчанию 30 дней назад);
- «Monthly impact at your volume»: месячный contribution сейчас − на дату сравнения (03 §6, шаг 10), объём из блюда; без объёма — «—» и блюдо исключено из итога; итог меню суммирует только заданные объёмы;
- отдельный список prep с себестоимостью за kg/l/pc, без contribution; необязательная подсказка “NL horeca average ≈ 30% (Sligro, 2025)” как справка, не цель;
- пометка подорожавших блюд;
- состояния «cost unknown» и «нет данных».

**Тесты:** core-формулы через `test:core`, компоненты через `test:ui`: функция «цены на дату», изменение contribution и monthly impact по шагу 10; блюдо без объёма не входит в итог; расчёты через заготовку для демо-данных. Браузерная проверка D9.
**Приёмка:** сценарий 1 из спецификации выполняется вручную, и цифры совпадают с тестом.

### Этап 6. Profit Simulator
**Цель:** ключевая функция продукта.
**Задачи:**
- выбор блюда;
- ввод объёма в месяц с безопасным целым ≥ 0 и оценкой владельца (не прогноз); начальное значение — `monthlyVolume`, если задан;
- сценарии A/B/C с правкой цены в меню, цен ингредиентов и граммовок;
- мгновенный пересчёт;
- таблица сравнения Baseline / A / B / C с разницей за порцию и за месяц;
- сохранение сценариев;
- пометка «Baseline changed»;
- явные подписи: «excl. VAT», «before other costs», «based on your sales estimate».

**Тесты:** core-формулы через `test:core`, интерфейс через `test:ui`; тест «после работы с симулятором ингредиенты и рецепты не изменились». Браузерная проверка D9.
**Приёмка:** сценарий 2 из спецификации выполняется вручную, а пример из ТЗ виден в интерфейсе.

## Реалистичность по срокам
- **За 3–4,5 дня реально:** этапы 0–6 и базовая версия этапа 7 (README и скриншоты); переход UI на React добавляет примерно 0,5–1 день.
- **Потребует больше времени:**
  - автоматические браузерные тесты Playwright (после MVP; до этого обязательна ручная проверка в реальном браузере);
  - тонкая мобильная полировка;
  - нидерландский язык интерфейса;
  - «влияние одной цены на всё меню сразу» вне Dashboard;
  - сохранение истории сценариев;
  - серверная версия с аккаунтами.

## Главные риски
1. **Ошибки в денежной арифметике.** Защита: `BigInt`, контракт округления, TDD на ручных примерах.
2. **Потеря данных в браузере** (очистка, приватный режим). Защита: предупреждение, экспорт и импорт, обработка ошибок записи.
3. **Несовместимость зависимостей или Tailwind/21st.dev-компонентов.** Защита: только утверждённые версии и лицензии, проверка peer deps, конфигов и импортов.
4. **Ошибки типизированной границы JS/TS.** Защита: явные readonly-типы и методы адаптера, `tsc --noEmit` обязателен в CI.
5. **Непонятная терминология для владельца.** Защита: фиксированный словарь терминов из спецификации, подсказки, ручная проверка владельцем после этапов 4b–6.
