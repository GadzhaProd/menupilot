# D3 — копии и восстановление: проверка

Дата: 2026-10-22 (Europe/Amsterdam). macOS, Node 25.8.1, SQLite 3.52.0.
Ветка: `bb/astra-d3-thr_f65kjfhah4`. База: main с D1/D2.

## Реализовано

- Durable dirty/dirtySince, очередь единственного писателя, автоснимки через
  `node:sqlite.backup()`, снимки на запуске/остановке, ежедневная точка без изменений.
- Проверка SQLite и доменных документов до fsync/атомарной публикации; metadata
  связывает копию с ID, ревизией, временем и структурой БД.
- Копия непосредственно перед import/reset/history restore/backup restore/migration;
  отказ замены при невозможности копирования. Миграция структуры БД 1→2 с pre-copy.
- Внешнее назначение: готовые копии, проверка приёмника, backoff, статус и EN/NL
  предупреждения, честный текст о неподтверждённой облачной синхронизации.
- `backup list|verify|restore <id>` через авторизованный API; подтверждение и `--yes`;
  restore создаёт новую ревизию, journal и receipt обычным CAS-протоколом.
- Offline `doctor --recover-from-backup <id>`: общий process lock, проверка,
  сохранение оригинала и WAL/SHM, durable intent для повторного восстановления,
  новый dataset ID, отчёт, права 0600 на восстановленную базу.
- Retention: сутки + 14 дневных точек; жёсткий бюджет 512 файлов/2 GiB. Ошибка
  бюджета видима, свежие точки не выбрасываются молча. Архивы аварийного протокола
  требуют ручного разбора, автоматически не удаляются.

## Что именно проверено при отказах

- Реальный дочерний процесс остановлен SIGKILL внутри progress callback SQLite
  backup, когда остаются страницы: готового `.sqlite` нет; после старта dirty
  revision копируется; partial очищается.
- Настоящий `SQLITE_FULL` через `max_page_count`: откат document/history/ops/dirty;
  ENOSPC на границе копирования: отказ destructive replacement и повтор после
  восстановления возможности записи. Это эмуляции, не заполнение системного диска.
- Конкурирующий save не вклинивается между pre-import snapshot и import; копия
  побайтно по структуре StoredDocument соответствует состоянию до импорта.
- Verify каждой копии сценария восстанавливает временную БД; проверяются
  повреждённый документ, неверная revision metadata и CHECK-corruption SQLite.
- На SQLite 3.52.0 read-only integrity_check пропускает CHECK-corruption;
  проверяем отдельную writable-копию без изменений. Регрессия и мутация это ловят.
- Restore увеличивает revision, сохраняет текущий ID, пишет journal/receipt,
  повторяет квитанцию без второго изменения. CLI требует подтверждение; без
  сервера предлагает npm start; doctor при живом сервере отказывается.
- Миграция с неудачной копией сохраняет v1; успешная сохраняет v1 snapshot перед v2.
- Внешняя недоступность/backoff, восстановление доступа, startup/shutdown,
  откат wall clock, обычный deadline, ежедневный снимок, retention/квота.
- Offline recovery сохраняет испорченный файл, делает новую идентичность и отчёт;
  прерванный intent блокирует старт и безопасно повторяется.
- HTTP body timeout заканчивается после получения тела и не выдаёт ложный 408
  во время долгой проверки копии (отдельная регрессия).

56 мутаций включают 13 новых D3: очередь, revision metadata, dirty, pre-copy,
startup/shutdown, restore revision, integrity_check, квота, backoff, deadline,
restore-test и emergency intent.

## Отчёт владельцу

1. Сделаны автоматические копии, проверка и два вида восстановления, видимый статус.
2. Это защищает сохранённую работу и позволяет вернуться к состоянию до замены данных.
3. Программа сначала проверяет копию, затем показывает её как готовую. Обычное
   восстановление создаёт новую версию данных; повреждённый файл сохраняется отдельно.
4. Запустить npm start, изменить ингредиент, подождать до 5 минут и проверить время
   в шапке; переключить EN/NL. В терминале backup list → backup verify ID. Для
   проверки восстановления использовать тестовые данные и backup restore ID.
5. Пройдены check, 56 мутаций, 23 обычных e2e и 2 локальных e2e; вывод выше.
6. Функциональных пунктов D3 не оставлено. Независимое ревью координатора ещё
   необходимо. Физическое отключение питания и облачная синхронизация не испытаны;
   новые CLI-функции D4/D5/D6 в этот этап не входят.

| Что защищено | Предел |
| --- | --- |
| Подтверждённое сохранение при сбое приложения | WAL + FULL; аппаратное отключение питания не проверено. |
| Ошибочный импорт/reset/restore/миграция | Копия непосредственно до замены, в пределах retention/бюджета. |
| Повреждение основной базы | Цель ≤5 минут при работающем сервере и здоровом хранилище; фактический предел — последняя успешная копия. |
| Потеря компьютера/диска | Нужна независимая внешняя копия. Локальные файлы на том же диске не спасают; облачную синхронизацию проверяет владелец. |
| Полный диск/недоступная папка | Нет ложного успешного сохранения; разрушительная замена отклоняется. При ошибках свежесть копии может выйти за 5 минут. |
| Часы назад/сон/остановленный сервер | Monotonic таймер и startup snapshot; календарные метки могут быть неверны, во сне расписание не выполняется. |
